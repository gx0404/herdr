上部バーの **Monitor**、メインメニュー、コマンド検索から開きます。1 つのパネルが System / Accounts / Monitor preferences の 3 ページを持ち、パネル内のタブまたは `1`/`2`/`3` で切り替えます。`r` は更新、`Space` は履歴の一時停止、`Esc` で閉じます。パネルのフッターにはこれらがクリックできるヒントとして並びます。更新は System と Accounts ページ、一時停止は System ページ、閉じるは全ページにあります。Monitor preferences ページはローカル設定だけなので、フッターに更新は表示しません。ハードウェアの指標は接続先ホストのものです。リモートの Agent にホバーすると、そのエージェントのホストで使用量を照会します。

## メニュー、ページと安定した選択

`prefix+Space` はカテゴリ別のメインメニュー、`prefix+/` はコマンド検索を開きます（既定の prefix は `Ctrl+B`）。カテゴリはワークスペースとエージェント、タブとペイン、マシンと SSH、監視と使用量、ツールと自動化、外観と設定、ヘルプと通知です。最近使ったコマンドは最大 5 件です。検索はどちらの表示言語のアクション名、ショートカット、カテゴリ名、マシンのアドレスにも一致します。ホイールは選択とは独立してスクロールし、キーボード操作は選択中の項目を表示範囲に入れます。

ページの上枠をドラッグすると移動し、左右と下の枠をドラッグするとサイズを変えられます。位置とサイズはクライアント設定に保存され、小さなターミナルでは画面内に収まるよう調整されます。レイアウトのロック中はページもドラッグできません。メニューを閉じると元のページに戻ります。設定は Enter または **apply** ボタンで反映され、テーマは選ぶとプレビューされ、Esc でプレビューを取り消せます。

ターミナルの文字を選択している間は、そのペインの文字スナップショットを固定し、プロセスとほかのペインは更新を続けます。マウスを離すとコピーしてライブ表示に戻ります。`copy_on_select` が無効なら、保持された選択を Ctrl+C でコピーします。スクロールは取得済みの履歴を読むだけで、ライブのターミナルはスクロールしません。取得前に出力が変わり、すでにマウスを離していた場合は、見ていない内容を自動でコピーせず、Ctrl+C で取得済みの選択を確定してもらいます。

スナップショット 1 件の上限は 65,536 セル、2048 行、8 MiB で、スクロールは取得した範囲の端で止まります。サーバー全体では 64 MiB、32 件、クライアントごとに 1 件です。サイズ変更、対象の変更、取り消し、切断でスナップショットは解放されます。確認されない取得は 60 秒で期限切れになります。古いサーバーでは従来の選択動作を使います。

WezTerm の leader には `Ctrl+Shift+Space` を使い、Herdr 用に `Ctrl+B` を残してください。通常のドラッグは Herdr 内の選択、Shift+ドラッグは WezTerm の選択です。

## ドック配置

パネルタイトルの `⠿` ハンドルを別のパネルの端へドラッグするとドックできます。ドロップのプレビューが移動先を示します。境界線をドラッグしてサイズを変え、タブをドラッグして並べ替えたり別の端末グループを作ったりでき、ペインのハンドルをドラッグすると、プロセスを再起動せずにペインを入れ替えたり別のタブへ移したりできます。枠のないペインのハンドルは **Arrange layout** モードのときだけ表示され、通常のターミナル本文を遮りません。タブの右クリックメニューも引き続き使えます。

プライマリの端末ページはフォーカス中のワークスペースに属します。サイドバーでワークスペースをクリックすると、タブ列と端末の内容がそのワークスペースのタブに切り替わります（番号はワークスペースごとに 1 から）。独立したパネルへドラッグしたタブは、ワークスペースのフォーカスにかかわらず表示されたままです。

`□` はパネルを最大化し、最大化中はボタンが `◫` になってレイアウトを元に戻します。上部バーの **Arrange layout** でレイアウト調整モードに入り、オンのあいだはボタンが強調表示されます。フッターにはモード名とキーが表示されます。`Tab` でパネルを選び（`Shift+Tab` で逆順）、矢印でサイズ変更、`Shift+矢印` で移動、`Enter` で最大化、`Esc` で終了します（フッターの **Esc done** もクリックできます）。パネルの最大化中もレイアウト全体が反応し、`Tab` は最大化をフォーカスと一緒に移し、矢印や `Shift+矢印` はいったん最大化を解除してからサイズ変更や移動を見せます。**Lock layout** はオン/オフの切り替えで、ロック中はチェックマークが付き、誤って並べ替えるのを防ぎます。調整モードのときだけ表示される **Reset** は既定のレイアウトに戻します。レイアウトはクライアントとエンドポイントごとに保存されます。小さいターミナルでは保存したレイアウトを捨てずに、フォーカス中のパネルだけを表示します。古いサーバーでは従来の単一ビューの UI を使います。

Monitor パネルのヘッダーには `□` の横に ` × ` ボタンがあります。ドックしたパネル内のページは独自の枠を描きません（パネルのヘッダーと区切り線がすでに枠になるため）。タブはパネルのヘッダーの下の 1 行目に、カードはパネルの端から 1 列内側に並びます。パネルにフォーカスがあるときは `Esc` でそのページを載せたパネルを閉じます。ターミナルにフォーカスがあるときは `Esc` はターミナルへ渡るので、ヘッダーのボタンかコマンド検索の **Close monitor panel**（Monitor パネルがドック中のときだけ表示）を使ってください。レイアウトがロックされていると閉じられず、パネルのフッターにその旨が表示されます。最後に選んだ Monitor のタブ（System / Accounts / Monitor preferences）はクライアント設定に保存され、パネルが再びフォーカスされたときやクライアントの再起動時に復元されます。上部バー、メインメニュー、コマンド検索から **Monitor** を開いたときは System ページから始まります。ドックした Monitor パネルは、フォーカス中のターミナルのカーソルを隠さなくなりました。カーソルが消えるのは、パネル、使用量のポップオーバー、ダイアログが実際にその位置を覆うときだけです。

上部バーが画面幅に収まらないときは、ボタンを途中で切らずに丸ごと隠します。**Monitor**、**Lock layout**、**Arrange layout** の順に隠し（3 つともメインメニューとコマンド検索から使えます）、上部バーにしかない **Reset** はそれらより後まで残します。

## リソース監視

CPU の合計・コアごと、RAM/swap、GPU、ディスク、ネットワークインターフェース、温度、プロセスを選べます。サンプリング間隔は 500、1000、2000、5000 ms です。遅い取得処理は独立して動きます。初回の差分サンプル、利用できないドライバー、権限の失敗は、0 ではなく状態または `—` で表示します。

NVIDIA は NVML を使います。Linux のほかの GPU はドライバーが公開する DRM/sysfs のフィールド、Windows は DXGI とネイティブの GPU パフォーマンスカウンターを使います。温度・電力・使用率を取得できるかはドライバー次第です。コンテナーと WSL はその環境で見えるリソースを表示します。

System ページの先頭はホスト概要の 1 行（ホスト名、OS、稼働時間、サンプルの経過時間、サンプリング間隔）で、その下にリソースカードを 1 列、パネル幅が 96 列以上なら 2 列で並べます。CPU カードは全体のゲージ（数値はどの幅でも残ります）、モデル名（コアをクリックするとそのコアの説明に置き換わります）、履歴スパークラインを表示し、コアごとのカードは論理コアごとのミニバーをカード幅いっぱいに並べ、コアをクリックするとその履歴を選びます。メモリは使用中とキャッシュを 1 本のゲージの区分として描き、swap のゲージも付きます。GPU はデバイスごとに温度・使用率・VRAM を並べます。ディスクは実データのボリュームだけの表で、容量のない疑似ファイルシステムは除外し、複数箇所にマウントされた同じデバイスは 1 回だけ載せます。ネットワークはアクティブなインターフェースごとに受信 / 送信を重ねたスパークラインを描き、アイドルなインターフェースは 1 行にまとめます。温度はチップごとに要約します。数値とバーはチップ内で最も熱いセンサーを示し、その後にチップの平均温度が続きます（パネルが狭いと平均から省きます）。すべてのチップが収まり 2 行以上余るときは、その下に最も熱いセンサーの履歴を描きます。同じカード内のバー行はラベル列と数値列を共有するため、バーの始点と終点がそろいます。プロセスはヘッダーのクリックで並べ替えられる表で、その上の行に名前フィルターと表示範囲があります。PID 列はサンプル中で最も長い PID に合わせた幅になり、7 桁の PID も切れません。カード内でスクロールすると追加のデバイス・コア・プロセスを表示します。CPU やメモリのように内容がすでに収まっているカードの上では、ホイールはページをスクロールします。ページのそれ以外の場所では、ホイールとカード未選択時の `↑`/`↓` がカード 1 行ずつ、`PageUp`/`PageDown` が 1 画面ずつスクロールします。最後のカードが完全に見えた所で止まるので、逆方向の最初の 1 目盛りですぐ動きます。それまでは次の行のカードがページ下端から上部だけ見え、低いカードに押し縮めず下端で切り取って表示します。Monitor preferences ページは 1 目盛り 3 行でスクロールし、同じく最終行で止まります。履歴はクライアント内に保持され、1–60 分、上限 16 MiB です。一時停止は履歴の記録だけを止め、ライブのサンプリングとアラートは続きます。

カードの順序は、概要行の右端のボタンから入る **Edit layout** モードで変更します。各カードの上辺に ↑/↓ ボタンが現れ、カードを 1 つ選ぶと他は淡色になり、`↑`/`↓` キーで選択中のカードを動かします。**Done** または `Esc` でモードを抜け、パネルが閉じるのは次の `Esc` です。カードの高さ、非表示のデバイス、チャートの字形は Monitor preferences ページで設定します。

プロセスの詳細はプロセスのインスタンスに固定されます。終了には確認が必要で、強制終了は別の選択肢です。期限切れの確認、再利用された PID、保護されたプロセスは拒否されます。Windows での終了には強制オプションと適切な権限が必要です。

アラートは既定でオフで、TUI が接続している間だけ動作します。しきい値、継続時間、クールダウンを設定でき、アラートがプロセスを終了することはありません。Monitor preferences の行とアラートの通知は、ルールを設定の id ではなくメトリクス名（CPU、Memory、GPU、Disk）で示します。

**Monitor preferences** ページはコントロールをカードにまとめます。サンプリング間隔（500 / 1000 / 2000 / 5000 ms）、カードの高さ（7 / 10 / 16 / 24 行）、履歴範囲（1 / 5 / 15 / 30 / 60 分）、ホバー遅延、各アラートルールのしきい値（50–100 %、5 刻み）・継続時間・クールダウンはステッパー、アラート、プロバイダーのアカウント使用量、表示するカード、表示するプロバイダー、取得するデバイスはトグル、使用量の形式・配置とチャートの字形はセグメントコントロールです。ステッパーは固定の段階表の隣の段へ移動し、両端で折り返すので、段階の間にある設定値は段を飛ばさず最初に隣の段へ移ります。**Chart glyphs** は System ページのスパークラインとバーの字形——Braille（既定）、Blocks、それらの字形がないターミナル向けの ASCII——を選び、クライアント設定 `monitor_chart_glyphs` として保存されます。

```toml
[monitor]
interval_ms = 1000
history_minutes = 15
visible = ["cpu", "cores", "memory", "gpu", "network", "processes"]
card_height = 10
hidden_devices = []
alerts_enabled = true # 既定: false

[[monitor.alerts]]
metric = "cpu" # cpu / memory / gpu / disk
threshold = 90
duration_seconds = 30
cooldown_seconds = 60
```

`visible` には `cpu`、`cores`、`memory`、`gpu`、`disks`、`network`、`sensors`、`processes` を指定でき（既定は 8 つすべて）、アラートの `metric` は `cpu`、`memory`、`gpu`、`disk` のいずれかです。`[[monitor.alerts]]` を書くと組み込みのルール（CPU・メモリ・ディスクは 90 %、GPU は 95 %、いずれも 30 秒継続・クールダウン 60 秒）が置き換わります。Monitor preferences ページでサンプリング間隔、カードの高さ、履歴範囲、表示するカード、取得するデバイス、アラートの設定を変えるか、**Edit layout** でカードを動かすと、監視の設定全体がクライアント設定 `monitor` として保存され、以後は設定ファイルの `[monitor]` より優先されます。**Restore config file values** が戻すのはアカウント使用量の設定だけです。

## アカウントの関連付け

Agent 行または CLI タイトルにホバーすると使用量を確認できます。`format` はダッシュボード（ゲージ）か表かを選びます。`position` はペインごとのポップオーバーの置き場所を決めます。`hover` と `both` は Agent 行と CLI タイトル上のポップオーバーを保ち、`page` はポインターによるポップオーバーを無効にして、ペインごとの表示をアカウントページと後述の右クリック **Usage** カードだけにします（選択中は Monitor preferences ページにヒントが表示されます）。アカウントページはどの値でも使えます。Monitor → Monitor preferences で行った選択はクライアント設定として保存され、そのマシンでは **Restore config file values** を使うまで `enabled`、`format`、`position`、`hover_delay_ms`、無効化したプロバイダーを上書きします。アカウントを選んでペインに関連付けてください。同じベンダー名というだけではアカウントを特定しません。未関連付けのペインから公式コールバックが届き、そのベンダーに設定済みアカウントがちょうど 1 つだけなら、server はペインをそのアカウントに関連付けて保存し、スナップショットに自動関連付けと表示します。アカウントが複数ある場合、コールバックは候補の一覧とともに拒否され、明示的に関連付ける必要があります。自動関連付けには `account_usage.enabled` と、公式コールバックの場合はクォータ項目を含むコールバックが必要です。

Agent 行と CLI タイトル上のペインごとの使用量ポップオーバーは `hover_delay_ms`（既定 400 ms）の経過後に表示され、ポインターが行とポップオーバーから離れて 250 ms 後に閉じます。独自のスコープを持ち、表示したりそこで関連付けたりしてもアカウントページの選択は変わりませんが、ポップオーバーの **Switch account** はアカウントページの選択も切り替えます。**Open page** ボタンでアカウントページが開きます。プロバイダー横断の概要はアカウントページにあり、先頭のチップ **All providers** で表示中のすべてのプロバイダーをまとめて表示します。概要に表示するアカウントがないときは、プロバイダーの選択を促す代わりに理由を示します。ホストにプロバイダーの CLI も設定済みアカウントもない、表示中のプロバイダーがすべて Monitor preferences でオフになっている、照会中である、または表示中のプロバイダーに照会できるアカウントがない、のいずれかです。特定のプロバイダーを選んでいてアカウントがないとき（Agent 行の使用量カードを含む）も同様に理由を示します。Monitor preferences でオフになっている、このホストにその CLI も設定済みアカウントもない（server はインストール済みのプロバイダーにだけアカウントを作ります）、このホストがその使用量を提供していない、または照会への応答に照会できるアカウントがなかった、のいずれかです。"Querying" は最初の応答が届くまでだけ表示され、概要でも同じです。

同じカードは意図して開くこともできます。Agent 行を右クリックして **Usage** を選ぶと、カードがすぐに表示されてピン留めされたままになります。タイトルは `<agent> · Usage` で、上枠の右端に **pinned** マークが付きます。ポインターを離しても、ほかの Agent 行の上を通っても閉じたり置き換わったりせず、Esc キーかカードの外側のクリックで閉じます。この項目は `page` を含むどの `position` でも使え、クラシックレイアウトでは開いている監視ページの上にもピン留めしたカードが描かれます。Monitor preferences でアカウント使用量をオフにしている場合、カードは読み込みを続けずにその旨を表示します。Agent 行から開いたカード（ホバーでもピン留めでも）は Agents パネルの横に表示されます。通常は右側で、パネルが右端にドックされているときは左側です。行のすぐ下の行から始まり、下に収まらないときは行のすぐ上の行で終わるので、隣の Agent 行を覆いません。パネルの両側とも 40 列の空きがないときは、行の真下または真上に開きます。CLI タイトルから開いたカードはタイトル行の真下に左揃えで開き（右端に近すぎるときは左へずらします）、下に収まらないときはタイトルの上へ反転します。上下どちらも高さが足りないときは広い側で縮めて表示し、5 行未満になるカードは表示しません。カードが自分の行やタイトルを覆うことはありません。

クライアント設定はフィールドごとに読み込まれます。読み取れない値（例: 未知の `usage_format` や `monitor_chart_glyphs`）は、そのフィールドだけが 1 回の診断とともに破棄され、残りは保持されます。`usage_*` キーは明示的に設定した場合にのみ書き戻されます。

アカウントページには、接続先ホストに公式 CLI がインストールされているプロバイダーだけが表示されます。判定には設定のインテグレーションページと同じ、複数の別名による PATH の検索とインストールレイアウトの確認（codex の standalone/nvm/volta/bun など）を使うため、両画面の結果は一致します。ZCode には探す CLI がないため、接続先ホストにそのローカルデータベース `~/.zcode/cli/db/db.sqlite` がある場合に表示されます。アカウントを明示的に設定したプロバイダーは表示されたままです。`account.usage.providers` はプロバイダーごとに `installed` フラグを返し、古い server はこのフィールドを省いてレジストリ全体を表示し続けます。自動更新はクライアントがデータを表示している間、server 側で実行されます。API アカウントは `api_refresh_seconds`（最低 60 秒）ごと、CLI プローブは `cli_refresh_seconds`（最低 300 秒。実効値は `account.usage.providers` が `minimum_interval_seconds` として告知し、ZCode のローカルデータベースの読み取りも同じ周期です）ごとに照会し、失敗後は上限付きのバックオフがかかります。公式コールバック（Claude Code）または Herdr 自身のインテグレーション拡張（Pi）からデータが届くベンダーはポーリング間隔を告知せず、そのプッシュで更新されます。プロバイダー未選択でアカウントページを開くと、フォーカス中のペインで動いているエージェントを選び、なければ最初に表示されているプロバイダーを選びます。プロバイダーやアカウントを切り替えると、新しいデータが届くまで以前のスナップショットを淡色で表示します。現在のスコープに設定済みアカウントが 2 つ未満なら **Switch account** は無効になり、設定でオフにしたプロバイダーはプロバイダーのチップ、切り替え候補、概要から即座に消えます。インストールレイアウト経由で codex CLI を見つけた場合、プローブはそのレイアウトの bin ディレクトリを `PATH` の先頭に付けて実行し、npm shim の CLI がインタープリターを解決できるようにします。

パネルが広い場合（96 列以上）、詳細カラムには選択中のアカウントで最も厳しいクォータ枠の推移も描かれます。クライアントは直近 120 サンプル（ポーリングの応答と購読のプッシュの両方）を保持し、"Usage history" の見出しの下に、カラムに収まる最新の分をスパークラインで描画します。サンプルが 8 個未満のうちは 1 行の帯だけを描き、それ以上あっても最大 6 行の小さなグラフにとどめ、カラム全体に引き伸ばしません。

明示的な更新（`account.usage.refresh`、アカウントページの更新操作、プロバイダーやアカウントの切り替え）はアカウントごとに 10 秒のデバウンスがかかり、ベンダーのバックオフ（HTTP 429）にも従います。デバウンスされた応答には `next_allowed_at_ms` が含まれます。終端結果（未ログイン、未対応、権限なし）は低頻度で自動的に再試行され（10 分から倍々で最大 1 時間、最大 6 回）、CLI 本体や資格情報ファイルが変わると保留はすぐに解除されるため、ログインすれば再起動なしで回復します。明示的な更新は終端状態でも常に再試行します。クォータ項目のない公式コールバックはキャッシュ済みのサンプルを上書きしません。コールバックが 15 分間ないとスナップショットはキャッシュ表示になります。プローブにフォールバックすることはありますが、それを置き換えるのは成功したプローブか次のコールバックだけです。プッシュでデータを得るベンダー（`interactive_probe` がオフのときの Claude Code の公式コールバック、Pi の拡張のプッシュ）は更新状態に `callback_only` を報告します。明示的な更新ではこれらの新しいサンプルは得られませんが、ログインや関連付けのプレースホルダーは更新されることがあります。

アカウントページが表示されている間、クライアントは `account.usage.subscribe` を告知する server で購読し、プッシュされる `account.usage.updated` / `account.usage.refreshing` イベントを届いた時点で反映して、30 秒のフォールバックポーリングだけを残します。購読はページが隠れると解除され、再接続後に張り直され、古い server ではポーリング（2 秒、プローブ実行中は 500 ms）にフォールバックします。プローブ中のアカウントは状態の代わりに "Refreshing…" を表示します（カードのバッジ、ローカル / セッション統計のカードでは状態行、表形式では状態列）。そのため "Current" と "Refreshing…" が同時に表示されることはなく、カードにはデータの経過時間がそのまま表示されます。更新ボタンは、選択中のアカウント（未選択なら表示中のすべてのアカウント）がデバウンス中のあいだ "Refresh in Ns" と表示し、1 分を超えるベンダーのバックオフはボタンをロックせずアカウントの行に注記します。アカウントページには関連付けの行もあります。選択中のプロバイダーのエージェントを動かしているペインだけを示すペインの選択、"Bind focused pane"、未関連付けのペインからのコールバックを server が拒否した後に出る `pending_binding` のワンクリック候補です。どの入口も別のプロバイダーのエージェントを動かしているペインを拒否し、公式コールバックを有効にしたときの関連付けは応答したホストのペインに対して行われ、その間にアクティブになった別のホストには行われません。

Claude Code はコールバック優先です。クォータは公式 statusline コールバックから取得し、プローブは非対話の `claude auth status --json` でログイン状態だけを確認します（実際のログイン情報を読み取り専用で参照します）。ログイン済みでコールバックのないアカウントは公式 statusline コールバックを待っていると表示され、コールバックはアカウントページの **official callback** トグルで有効にします。最初のコールバックが届くまで、この事前確認は終端状態と同じ低頻度のスケジュールで間隔を空けます。対話式の `/usage` プローブはオプトイン（`interactive_probe = true`）で、明示的な更新のときだけ、herdr の状態ディレクトリ配下の固定のプローブディレクトリで実行されます。Claude Code はそのディレクトリの信頼を自分の CLI で一度だけ確認するよう求めます（更新状態は `trust_required` を報告し、メッセージにディレクトリが示されます）。herdr がそのダイアログに代わりに応答することはありません。対話式プローブは実際のログイン状態を再利用するため、同時に起動すると資格情報がローテーションされることがあります。コールバックなしで `/usage` が必要な場合以外はオフのままにしてください。

コールバックは `rate_limits` のアカウント枠（`five_hour`、`seven_day`、Claude apps gateway 配下の `spend_limit`）に加えて、報告元セッションの推定費用・経過時間・API 時間（`cost.*`）とコンテキストウィンドウ（`context_window.*`）も運びます。これらはセッション統計として表示され、アカウントのクォータとしては扱いません。複数のセッションが 1 つのアカウントを共有している場合は、最後に報告したセッションの値です。公式 statusline の仕様に沿った点が 3 つあります。枠が `resets_at` を過ぎると Claude Code はその枠を JSON から外す（セッションの最初の API 応答までは `rate_limits` 自体がない）ため、欠けた枠は 0 にせず前回の値を保持し、リセット時刻を過ぎたらその旨を表示します（保持はリセット時刻から 1 週間まで、`resets_at` のない枠は最後に現れてから 1 週間までです）。`context_window.current_usage` と `used_percentage` は最初の API 呼び出しの前と `/compact` の直後に `null` になり、0 ではなく "no data yet" と表示します。`spend_limit` は 100 % を超えることがあり、報告値のまま保持します。`rate_limits` をまったく含まず（古い CLI や API キーでのログイン）、引き継げる枠もないコールバックは、そのアカウントの表示を置き換えません。

ダッシュボード形式ではアカウントごとに 1 枚のカードを、プロバイダーごとの配置で描きます。カードの上枠にアカウント名と状態、カード内の 1 行目にサンプルの経過時間・プラン・アカウント識別子（バッジが統計の注記の場合は状態も）を表示します。Claude Code は 5 時間・週間・利用額上限の 3 つの枠をゲージで描き、続けてセッションのコンテキスト使用量と費用を表示します。利用額上限は 100 % を超えても報告値のまま表示し、バーの末尾に超過マーク `▸` を描きます。リセット時刻を過ぎた枠は前回の値をグレーで保持し、バーを淡色にして "past reset" と注記します。Codex はレート制限のバケットごとに主 / 副の枠（枠の長さで命名。例: "5h window"）とそのバケットのクレジットを描き、バケットが複数あればそれぞれを節に分けます。Kimi Code は 5 時間・7 日・月間の枠、通貨単位の残高、追加使用量のウォレットを描きます。OpenCode と ZCode のカードには "Local stats, not account quota" のバッジが付き、数値（セッション数、費用、トークン、ツール呼び出し）をゲージなしで表示します。Pi のカードには "Session stats" のバッジが付き、コンテキストのゲージ、セッションの費用とモデル、トークンの内訳を表示します。最初のプッシュが届くまでは、カードが何を待っているかを説明します。ZCode のカードは、接続先ホストが ZCode のアカウントを報告した場合にだけ表示されます。カードが認識しないメトリクスも汎用の行として表示し、未知のプロバイダーには汎用のカードを使います。ゲージはしきい値で色分けし、枠の経過分を示す目盛りを描き（5 時間・週間・7 日の枠は固定の長さで、その他の枠はプロバイダーが長さを報告した場合のみ）、使用量が経過時間より先行すると早めに黄 / 赤になります。パネルが狭いと、数値より先にバーを縮めて消します。数値の行はラベルと数値の組を丸ごと扱い、収まらない組は途中で切らずに省いて、残りの組を詰めて並べます。ダッシュボード形式で **All providers** を選び、複数のプロバイダーのアカウントがあるときは、プロバイダーごとの小さなカード（最も厳しいクォータ枠、ローカル / セッション統計では主要な数値、と状態の 1 行）に切り替わり、96 列以上では 2 列に並べます。小さなカードをクリックするか、選んで Enter を押すとそのプロバイダーを開きます。Agent 行のポップオーバー内のカードはポップオーバーより高くならず、収まらない行は下枠に "+N" として数えられ、**Open page** でカード全体を確認できます。ポップオーバー自体は内容に必要な高さ（最大 17 行）しか取らないため、短いカードの下に空白は残りません。

どちらの形式もホイールでスクロールでき、アカウントページではビューポートより下のクォータ枠を矢印キーでも見られます。使用量のポップオーバーはフォーカス中の監視パネルの上にも表示でき、背後のカードやプロセス行を操作せずに自分の入力を受け取ります。

契約の枠、キーの予算、組織の請求、ローカルのセッション統計は、それぞれのスコープと単位を保ちます。結果にはリセット時刻、ソース、サンプルの経過時間が表示されます。一時的なエラーでは最後に成功したサンプルをキャッシュ状態で保持し、上限のある間隔で再試行します。

アカウントはエージェントを動かしている server で設定します。`credential_env` には環境変数名を書き、資格情報そのものを TOML に書かないでください。Herdr は CLI の OAuth 資格情報をクライアントにコピーしません。CLI のプロファイルは、ベンダーが文書化しているディレクトリの指定方法を使います。Kimi Code は `KIMI_CODE_HOME` を使い、ログイン状態はそのディレクトリの `credentials/kimi-code.json` にあります。そこでログインすれば、"Sign in required" のアカウントは再起動なしで回復します。

```toml
[account_usage]
enabled = true
format = "dashboard" # dashboard / table
position = "hover" # hover / page / both。page は Agent 行のポップオーバーを無効にします
hover_delay_ms = 400
api_refresh_seconds = 60
cli_refresh_seconds = 300
probe_timeout_seconds = 20
interactive_probe = false # 明示的な更新のみ。Claude はフォルダーの信頼が一度必要です
disabled_providers = []

[[account_usage.accounts]]
id = "work-codex"
label = "Work"
agent = "codex"
provider = "codex"
auth_mode = "cli"
profile_dir = "/path/to/profile"

[[account_usage.accounts]]
id = "team-api"
label = "Organization API"
agent = "claude"
provider = "anthropic"
auth_mode = "api"
credential_env = "ANTHROPIC_ADMIN_KEY"
```

OpenAI の API アカウントでは、`organization` で組織を選びます（`OpenAI-Organization` ヘッダーとして送られます）。`account_user` は非推奨です。これを使うプロバイダーはないため無視され、設定したままのアカウントには削除を促す設定診断が表示されます。API キーのアカウントは OpenAI、Anthropic、Moonshot、OpenRouter に対応します。OpenRouter では管理キーと `billing_scope = "account"` を使い、既定のスコープは現在の API キーです。`base_url` は登録済みの公式ホストだけを受け付け、Kimi のローカル API は loopback に限られます。

## 公式コールバック

Claude Code のアカウントパネルから公式 statusline コールバックを有効化・削除できます。既存の描画コマンドはパススルーのパイプラインの末尾に残します。Claude のクォータ項目には対応する CLI バージョンが必要で、通常は最初の通常の API 応答の後に現れます。Herdr が使用量を得るためにモデルへプロンプトを送ることはありません。

ほかのインテグレーションは、対応する公式 JSON を `herdr api usage-report --agent <agent>` の stdin に送れます。コマンドは `HERDR_PANE_ID` の関連付け、または明示的な `--account <id>` を使います。未関連付けのペインは、そのベンダーに設定済みアカウントが 1 つだけのときにだけ自動で関連付けられ、それ以外は先に関連付けてください。生のレポートや会話の内容は保存されません。`--passthrough` は既存の statusline の描画コマンドのために入力をそのまま渡します。

Pi には statusline の仕様がなく、RPC モードは別のヘッドレスプロセスを起動するため、ペインで実行中のセッションを参照できません。そこで Herdr の Pi 拡張（統合バージョン `10`。`herdr integration install pi` で更新）が実行中の TUI セッション内で使用量を読み取り、Herdr ソケット経由でプッシュします。タイミングはセッション開始時、各ターンの終了後（最大 5 秒に 1 回）、コンパクション後、エージェントが落ち着いた時です。内容はコンテキスト使用量（`ctx.getContextUsage()`）、セッションのトークンと費用の合計、現在のプロバイダーとモデル（要求したモデルと実際に応答したモデルが異なる場合は応答した方）です。Pi はマルチプロバイダー CLI なので、これはセッション統計であり、アカウントのクォータではありません。プロバイダー / モデルは、このセッションを実際に支払っている契約アカウントへ関連付けるためのもので、二重に計上するためではありません。コンパクション直後から次の応答までは Pi 自身もコンテキストサイズを把握しておらず、Herdr は 0 ではなく"no data yet"と表示します。Pi にコールバックのスイッチはなく、最初のプッシュが届くまではアカウントに待機理由が表示されます。

## 対応範囲と公式資料

アカウント使用量は Codex、Claude Code、Kimi Code、OpenCode、Pi、ZCode の 6 つのエージェントを対象にしています。公式資料の最終確認は 2026-09-22（Codex は 2026-09-16、ZCode のデータベース構造は 2026-09-23）です。サブスクリプションのアクセスと管理者の請求アクセスは異なります。未対応のバージョン、存在しない API、権限不足は利用できない旨を明示し、それ以外のエージェントに設定したアカウントは公式ソースが登録されていないと報告します。セッション統計とローカル統計がアカウントのクォータを意味することはありません。

| Agent | 公式ソースと範囲 |
| --- | --- |
| Codex | [App Server](https://learn.chatgpt.com/docs/app-server) のアカウント、レート制限の枠、クレジット。API の課金は管理者レポートを使います。 |
| Claude Code | [statusline JSON](https://code.claude.com/docs/en/statusline)：`rate_limits` のアカウント枠と、セッションの `cost`・`context_window`。公式 `/usage` はオプトイン。API 組織の使用量と費用は別扱いです。 |
| Kimi Code | [ローカル Server API](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/server-api.html)（公式に experimental）：`quota.usages` の 5 時間・7 日・月間の枠と、月間枠のうち Code の分。`quota.extraUsage` の従量課金ウォレットは金額で表示します（残高、総額、今月の費用、有効な場合は月間上限）。Moonshot API 残高は別途照会します。 |
| OpenCode | [`opencode db <query> --format json`](https://opencode.ai/docs/cli/)：`session` テーブルの読み取り専用集計（セッション数、サブエージェントのセッション数、費用、入力 / 出力 / 推論 / キャッシュのトークン）。ローカル統計であり、アカウントのクォータではありません。 |
| Pi | Herdr の Pi 拡張（公式の[拡張 API](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md) を使用）：コンテキスト使用量、セッションのトークンと費用、現在のプロバイダー / モデル。セッション統計であり、アカウントのクォータではありません。 |
| ZCode | [ZCode デスクトップアプリ](https://github.com/zai-org/ZCode)のローカルデータベース `~/.zcode/cli/db/db.sqlite` を、システムの `sqlite3 -readonly` で読み取り専用に照会します。`model_usage` テーブルの直近 24 時間分：メインタスクとサブエージェントに分けたトークンとその合計、ツール呼び出し回数、サブエージェントのセッション数。資格情報は不要で、読み取りもしません。ローカル統計のみで、アカウントのクォータではありません。リモートのクォータは照会しません。 |

OpenCode にはアカウントのクォータの API がないため、どちらの形も、メトリクスのスコープとソース表示でローカルのセッション統計と明示します。`db` のクエリは件数と合計だけを読み、セッションのタイトルやパスは読みません。`db` サブコマンドやその `--format` フラグがない CLI、またはクエリが失敗した場合（古いデータベース構造など）は、`opencode stats` の表の解析にフォールバックします。OpenRouter のキー予算はアカウントの合計とは別です。Kimi の Server API は公式に experimental とされているため、欠けている項目や形の違う項目はサンプル全体を失敗にせず、その項目だけを飛ばします。

アカウントページでは OpenCode と ZCode に「Local stats, not account quota」、Pi に「Session stats」のバッジが付き、いずれもアカウントのクォータとしては扱いません。ZCode のローカル統計は ZCode デスクトップ版のデータベースから読み、リモートのクォータは照会しません。

ZCode はペインで動かないデスクトップアプリで、Herdr がそれを起動することはありません（そのコマンドはウィンドウを開きます）。server は自身の `PATH` 上の `sqlite3` コマンドでデータベースを読み取り、コマンドがない場合は ZCode のアカウントに数値の代わりにその理由を表示します。クエリはリクエスト行を開始時刻で数えて合計するだけで、プロンプト、メッセージ、エラー本文は読みません。`query_source` が `subagent`、または `task_type` が `subagent_child` のリクエストはサブエージェントに、それ以外（メインターン、タイトル生成、コンパクション）はメインタスクに数えます。データベースがロック中・読み取り不能・構造変更の場合は、前回のサンプルをキャッシュとして保持し、バックオフ付きで再試行します。ZCode のアカウントは `herdr api usage-report` のプッシュを拒否し、`profile_dir` にも対応しません。ポーリングを止めるには `disabled_providers` に `"zcode"` を追加します。

## API

公開している JSON メソッドには `system.metrics.get/subscribe/unsubscribe`、`system.process.list/get/terminate`、`account.usage.providers/get/refresh/subscribe/unsubscribe/report/integration`、`account.binding.set` があります。遅い購読者には最新のサンプルだけが残ります。

`account.usage.get` / `account.usage.refresh` の応答と `account.usage.updated` イベントは、スナップショットと並べて `refresh` リスト（`UsageRefreshState`。`account_id` で `accounts` と対応し、古い server では省略）を返します。プローブの進行（`in_flight`、`queued`、`attempted_at_ms`）、明示的な更新のデバウンス（`requested_at_ms`、`next_allowed_at_ms`）、ベンダーのバックオフ（`retry_after_ms`）、`binding_inferred`、`trust_required`、`callback_only`、`pending_binding`、`callback_enabled` を含みます。`account.usage.refreshing` はプローブの開始時にこのリストだけをプッシュします。フィールドの意味とイベントのエンベロープは[イベント購読](/ja/docs/socket-api/#イベント購読)を参照してください。

`client.views.set` とビューのフレーム/入力の名前付き拡張には、ネゴシエーション済みの TUI 接続が必要です。generation 1 のエンコードは変わりません。ペインのドラッグは既存の `pane.move` と `pane.swap` を使います。詳しい契約は `herdr api schema --json` を参照してください。
