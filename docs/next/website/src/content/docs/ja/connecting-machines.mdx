title: マシンへの接続
description: Local と保存済み SSH マシンを 1 つの Herdr ウィンドウで操作し、エージェントをまとめて確認できます。各接続は独立して再接続します。
---

ローカルの作業とリモートのエージェントを、1 つの Herdr ウィンドウにまとめられます。SSH マシンを一度保存すれば、別のクライアントを開かずに、そのワークスペースと Local を切り替えられます。エージェント一覧には接続中のマシンが含まれ、作業場所や回答待ちのエージェントを確認できます。

各マシンは独自の Herdr サーバー、セッション、プロセスを保持します。1 台への接続が切れても、ほかの接続は切れません。

## 接続前の確認

リモートマシンへの通常の SSH アクセスが必要です。最初に確認してください:

```bash
ssh workbox
```

`workbox` は SSH config のホスト名です。`ssh://you@server:2222` のような接続先も使えます。

複数マシンへの接続は Linux と macOS のクライアントで対応しており、x86_64 または aarch64 の Linux と macOS サーバーに接続できます。Windows での複数マシンへの接続は未検証・未対応です。単独接続の `herdr --remote` は引き続き Windows でも対応しています。ネイティブ Windows サーバーは SSH 接続先として未対応です。SSH 設定、認証、カスタムバイナリについては [SSH 越しのリモートアタッチ](/ja/docs/persistence-remote/)を参照してください。

## マシンを追加する

インストールや置き換えの前に確認できるよう、対話型ターミナルで実行します:

```bash
herdr machine add workbox --label "Build machine"
```

リモートのデフォルトセッションを使います。1 つのプロファイルは 1 つのリモートセッションを対象とし、そのホストの全セッションをまとめるものではありません。

名前付きセッションを使いたい場合だけ、任意の `--remote-session` を追加します:

```bash
herdr machine add workbox --label "Build machine" --remote-session agents
```

Herdr はインストール済みバイナリと実行中サーバーをそれぞれ確認し、対象のバックグラウンドサーバーを起動してからプロファイルを保存します。互換性があればクライアントとサーバーのバージョンは一致しなくても構いません。未インストールや非互換の場合は、承認付きのセットアップを行います。実行中サーバーの置き換えが必要なら、サーバーとペインのプロセスを停止する前に確認し、その後に互換サーバーを起動します。デフォルトの回答は No です。インストールと置き換えの両方が必要な場合は、1 回の確認で承認します。`machine add` は実験的なライブハンドオフを使いません。セットアップをキャンセルした場合や失敗した場合、プロファイルは保存されません。

`herdr` で UI を開きます。ローカルクライアントがすでに開いていれば、追加や有効化したマシンは通常 1 秒以内に表示され、選択を変えずにバックグラウンドで接続します。マシン切り替え中の変更は、切り替えの完了後に反映します。セットアップ終了後もリモートサーバーは動き続けます。

## SSH 設定からマシンをインポートする

`~/.ssh/config` にすでにホスト定義がある場合は、設定を打ち直す代わりにインポートできます:

```bash
herdr machine import                     # 検出したホストを確認して取り込むものを選ぶ
herdr machine import --yes               # すべて取り込む（標準入力がターミナルでない場合に必須）
herdr machine import --host 'db-*' --group prod
herdr machine import --file ~/work/ssh_config
```

インポートは OpenSSH のセマンティクスで SSH 設定（`Include` されたファイルを含む）を読み取ります。各ディレクティブは最初の値が優先され、`Host *` がフォールバックを提供します。ホストのマッチングは大文字小文字を区別せず、`*`/`?` ワイルドカードと `!` 否定を使えます。`Match` ブロックは静的に評価できないためスキップします。SSH 設定は読み取り専用で、変更されることはありません。

各 `Host` は 1 つのマシンプロファイルになります。エイリアスがラベルに、解決された `HostName` がターゲットになり、`User`、`Port`、`IdentityFile`、`IdentitiesOnly`、`IdentityAgent`、`ProxyJump`、`ForwardAgent`、`ServerAliveInterval`、`ServerAliveCountMax`、`ControlPersist`、`RemoteCommand`、`StrictHostKeyChecking` がプロファイルのフィールドになります。これは `machine add` のフラグと同じ項目です。同じバッチでインポートされた別ホストを指す `ProxyJump` ホップは、そのホストへの `profile:<id>` 参照になり、それ以外のホップはリテラルターゲットのままです。`*.internal` のようなワイルドカードパターンは `--include-wildcards` を付けない限りスキップされ、インポートされたワイルドカードプロファイルは使用前に編集するテンプレートです。保存済みマシンやバッチ内のほかのホストとラベルやターゲットが重複するホストはスキップされ、ホストごとに報告されるため、インポートの再実行は安全です。

同じインポートは UI からも実行できます。マシンページで `i` を押す（またはコマンドパレットの「SSH 設定からマシンをインポート」）とウィザードが開き、検出されたホストとスキップ対象を理由つきで一覧し、インポートするホストをチェックし（スペースで切り替え、`a` で全選択/全解除、グループ欄でバッチ全体にグループを割り当て）、最後に各ホストのインポート済み/スキップ/失敗を理由つきで報告します。インポートされたマシンは CLI と同様にバックグラウンドで接続され、リモートサーバーのセットアップは別の明示的なステップのままです。ホストが画面に収まらない場合、選択ステップはスクロールし、ワイルドカードの切り替え・グループ欄・件数行は下部に固定されます。完了ステップも矢印キーでスクロールでき、末尾の項目が切れることはありません。

インポートはプロファイルの登録のみで、リモートサーバーのインストール・更新・再起動は行いません。インポート後のマシンはバックグラウンドで接続され、セットアップが必要なマシンはスタンドアロンのセットアップコマンドとともに Attention を表示します。1 台だけを `machine add` と同じ準備付きで登録する場合は次を使います:

```bash
herdr machine add --from-config web
```

SSH 設定から `web` を解決し、見つかったすべてのディレクティブで登録してから、通常どおりリモートセットアップを実行して保存します。接続オプションのフラグは `--from-config` と組み合わせられません。`--label`、`--remote-session`、`--group`、`--tag`、`--color` は引き続き使えます。

## マシンを切り替える

サイドバーでマシンまたはそのワークスペースを選びます。選択中のマシンだけがペイン入力とターミナルサイズを受け取り、表示するターミナル内容とグラフィックスを送信します。ほかの接続済みマシンは、ペイン画面を送らずにワークスペース情報、エージェント状態、通知を更新し続けます。

起動時は SSH 接続を待たずに Local を開きます。応答しないマシンがほかのマシンの入力を妨げることはありません。同じサーバーに接続した複数のクライアントは、それぞれ別のタブを表示できます。同じタブを表示した場合のサイズについては[クライアントとサーバー](/ja/docs/concepts/)を参照してください。

接続が切れると、最後のワークスペースとエージェント状態を暗く表示します。これはキャッシュであり、現在の状態ではありません。新しい接続と対応する画面が届くまで、そのペインへの入力や移動は無効です。再接続しても、使用中のマシンから選択を奪いません。

この入力ロックは意図的な設計です。リンクが切れている間、クライアントはセッションの状態を確認できないため、入力したキーが誤ったコンテキスト（進んでしまったシェル、別のプロンプト、実行中のエージェント）に届く可能性があります。ペイン入力を無効にしキャッシュ画面を暗くするのは、状態の不確かなセッションへキー入力を紛れ込ませないために、その境界を明示するためです。リモート側では何も失われません。リンクが切れている間もリモートの Herdr サーバーはセッション、エージェント、ペインプロセスを保持し、新しい接続が届けばワークスペースはそのまま再開します。自動バックオフを待ちたくない場合は、影響を受けているマシンの再接続バナーに 2 つの操作があります: **retry now** は即座に試行し、**give up** はそのマシンを無効化します（machines ページから再有効化できます）。

## 名前の変更、無効化、削除

ラベルやホスト名から推測せず、一覧からプロファイル ID を取得します:

```bash
herdr machine list
herdr machine rename <profile-id> --label "New name"
herdr machine disable <profile-id>
herdr machine enable <profile-id>
herdr machine remove <profile-id>
```

スクリプトでは `machine list` に `--json` を追加できます。

名前の変更は表示ラベルだけを更新し、再接続しません。無効化はプロファイルを残し、削除はプロファイルを忘れます。どちらもクライアントからそのマシンだけを切断し、到達不能なホストでも操作できます。リモートセッションとエージェントは動き続けます。

表示中のマシンを削除または無効化すると Local に戻ります。Local が利用できない場合は、別のリモートを選ばず、その状態を表示して再接続します。有効な保存済みマシンがあれば、Local が失敗または再起動してもクライアントを使い続けられます。

## シーンスナップショット

シーンスナップショットは現在の作業現場を保存し、後からワンアクションで復元できるようにします。対象は有効なマシンセット、アクティブなマシンとそのワークスペース・タブ（クライアントにキャッシュされたビューがある各マシン）、サイドバーの状態（幅・折りたたみ・グループの折りたたみ）です。コマンドパレット（「シーンを保存…」/「シーンを復元」）からスナップショットページを開き、`s` で現在のシーンを名前と任意のメモ付きで保存します。最大 32 件まで、endpoint カタログの隣にあるバージョン付き `scene-snapshots.json` に保存されます。

復元すると記録されたマシンが有効になります。「シーンに含まれないマシンを無効化する」トグル（`x`）は**既定でオフ**で、通常の復元ではスナップショットにないマシンを無効化しません。オンにすると、復元前に無効化・切断されるマシンを列挙した確認画面が表示されます。そこでの確認キーは `↵` ではなく `y`（または `ctrl+↵`）なので、Enter の長押しや連打で通り抜けることはできず、確認画面に列挙されたマシンだけが無効化されます。確認するまで endpoint カタログには何も書き込まれません。シーンがすでに有効なマシンをすべて含んでいる場合は無効化するものがないため、確認なしでそのまま復元されます。記録されたアクティブマシンとそのワークスペースがオンラインなら選択がそこに移り、オンラインのバックグラウンドマシンにも記録されたワークスペースのフォーカスが復元されます。スナップショットに名前があるがカタログに存在しないマシンは、失敗ではなくスキップされ、結果のトーストに一覧表示されます。

シーン一覧ではシングルクリックは行の選択だけを行います。復元は「復元」ボタン、`Enter`、または同じ行の 2 回目のクリックで実行されます。シーンの名前変更と削除も同じページから行えます。シーン名は一意で、保存も名前変更も既存の名前と衝突した場合はエラーとして拒否され、どちらのスナップショットも削除・上書きされません。

## ポートフォワーディング

保存済みマシンには SSH ポートフォワードのルールを持たせられます。接続と一緒に開始され、再接続時に再構築されます。ルールは CLI で管理するほか、UI ではマシン一覧またはマシンの詳細カードから入れます（`f` または「フォワード」ボタン）。詳細カードにはルールとライブ状態が並び、ルールページで追加・削除できます。ルールページは選択中のルールが見えるようスクロールし、`x` は対象のルールを示して `enter` の確認を待ちます（`esc` で取り消し）。確認中にルールが変わった場合、その位置に来た別のルールを削除せず、移除自体を取り消します。起動中のクライアントには再接続なしで約 1 秒以内に反映されます。

```bash
herdr machine forward list <profile-id>
herdr machine forward add <profile-id> --kind local --listen-port 8080 --target-host 127.0.0.1 --target-port 80
herdr machine forward add <profile-id> --kind remote --listen-port 9000 --target-host 127.0.0.1 --target-port 3000
herdr machine forward add <profile-id> --kind dynamic --listen-port 1080
herdr machine forward remove <profile-id> <rule-number>
```

3 種類のルールは `ssh -L`、`-R`、`-D` に対応します。

- `local` はこのマシンで待ち受け（デフォルトのバインドは `localhost`、`--bind-address` で上書き可能）、SSH マシン経由で `--target-host:--target-port` へ転送します。
- `remote` は SSH マシン上で待ち受け、このマシン側から到達するターゲットへ転送します。
- `dynamic` は SSH マシン経由のローカル SOCKS プロキシを開き、固定のターゲットはありません。

各ルールは接続本体と同じ生成 SSH 設定を使う独立した非対話の `ssh -N` 子プロセスとして動くため、オプションごとに `~/.ssh/config` が優先され、プロンプトが出ることもありません。起動できないルール（ローカルの待ち受けポートが使用中など）はそのルールだけが失敗し、理由が記録され、マシンの詳細カードとルールページで該当ルールの横に表示されます。接続や他のルールには影響しません。1 台のマシンにつき最大 16 ルールです。

## リモートファイル

保存した各マシンは、同じ管理 SSH チャネル経由でファイルシステムも公開します。バッチモードの OpenSSH `sftp` クライアントを使う仕組みで、設定・スクリプト・メモのような小さなファイル向けであり、大量転送向けではありません:

```bash
herdr machine fs build ls /srv/app
herdr machine fs build stat /srv/app/config.toml
herdr machine fs build cat /srv/app/config.toml
herdr machine fs build get /srv/app/config.toml ./config.toml
herdr machine fs build put ./notes.txt /srv/app/notes.txt
herdr machine fs build mkdir /srv/app/logs --parents
herdr machine fs build mv /srv/app/notes.txt /srv/app/notes-old.txt
herdr machine fs build rm /srv/app/notes-old.txt
herdr machine fs build rm /srv/app/old-logs --recursive
```

プロファイルの指定はラベルまたはプロファイル ID で、グローバルの `--machine` プレフィックスと同じ解決規則です。各操作はプロファイルの生成 SSH 設定、接続多重化、非対話オプション群を再利用するため、オプションごとに `~/.ssh/config` が優先され、プロンプトは出ません。リモートパスは sftp サーバーがログインディレクトリからの相対で解決し（`~` は展開されません）、`-` で始まるパスはオプションと誤認されないよう拒否されます。また `\` や `"` を含むパスは、バッチのクォート処理が OpenSSH のバージョン間で一貫しないため拒否されます。`ls` と `stat` は `--json` に対応しています。

転送は 1 ファイル 1 MiB までです。`get` はローカルファイルを `0600` 権限でアトミックに書き込み、シンボリックリンク経由の置き換えを拒否します。`put` は同じディレクトリの一時名にアップロードしてからターゲットへアトミックに rename し、ターゲットが既存の場合は以前のパーミッションビットを復元します。`mkdir --parents` は中間ディレクトリを作成します。`rm` でディレクトリを消すには `--recursive` が必要で、シンボリックリンクは辿らず、リモートのルートは拒否されます。SSH トランスポートの障害（認証・ホスト鍵・DNS・タイムアウト）は接続本体と同じ構造化された失敗種別で現れるため、壊れたマシンはコマンドをハングさせるのではなく UI に Attention と表示されます。

同じチャネルが UI 内のファイルブラウザも駆動します。マシン一覧またはマシンの詳細カードで `o`（または「ファイル」ボタン）を押すと開きます。ブラウザはリモートディレクトリを種別・サイズ・更新時刻付きで一覧し、Enter でディレクトリに入るかファイルを読み取り専用ビューアで開き（1 MiB までの小ファイル）、Backspace で上の階層へ、`r` で再読み込み、`/` で一覧を絞り込みます。`d` は選択したファイルを確認したローカルパスにダウンロード、`u` はローカルファイルを現在のディレクトリにアップロード、`m` はディレクトリ作成、`R` はリネーム、`x` は確認のうえ削除（ディレクトリは再帰削除）です。操作はすべてバックグラウンドワーカーで実行され、エラーはインライン表示されるため、UI は SSH でブロックされません。

## セッションログ

マシンのプロファイルは、そのペインをローカルのログファイルにミラーできます。監査証跡や、離れている間にエージェントが何をしたかの振り返りに使えます:

```bash
herdr machine log <profile-id> on
herdr machine log <profile-id> on --path "{machine}/{date}-{pane}.log" --max-bytes 16777216 --interval 30
herdr machine log <profile-id> show
herdr machine log <profile-id> dump
herdr machine log <profile-id> off
```

この仕組みは意図的にスナップショット方式です。クライアント側のワーカーが設定された間隔（デフォルト 30 秒）でマシンの JSON API ブリッジ経由ペインをポーリングし、ペインのリビジョンが変わったときだけスナップショットを追記します。UTC タイムスタンプ・マシン・ペイン・リビジョンを含む区切り行に、ペインの最近のテキスト最大 200 行が続きます。連続したバイトストリームではなく、2 回のポーリング間の高速な出力は最新の状態で表される、定期的な `pane read` に相当します。ワーカーは専用のブリッジを持つため、ログは表示中のマシンに依存せず、マシンの接続ライフサイクルに合わせて再起動します。

パスはテンプレートで決まり、`{date}`（UTC の日付）、`{machine}`（ラベルのスラッグ）、`{machine-id}`、`{pane}`、`{session}` の変数を使えます。相対テンプレートは `<state dir>/session-logs/` 以下に解決され、デフォルトは `{machine}/{date}-{pane}.log` です。ファイルはプライベート権限で作成され、サイズ上限（デフォルト 16 MiB）で `<file>.1` にローテーションされます。書き込みはすべて単一のバックグラウンドキュー経由で、ディスクが遅くてもペインが出力を氾濫させてもクライアントをブロックしません。キューが一杯のときは UI に背圧をかける代わりに、スナップショットを破棄してカウントします。ログの切り替えはプロファイルの `session_log` フィールドだけを編集するため、マシンを再接続しません。`dump` はスナップショットサイクルをちょうど 1 回すぐに実行し、追記したスナップショット数を報告します。テンプレートの検証はこれが最速です。

同じ設定は UI からも編集できます。マシンページの編集フォームの末尾にセッションログのフィールドがあり、オン/オフ/デフォルトの三択と、パステンプレート・サイズ上限・間隔（空欄はデフォルト）を設定できます。選択を**デフォルト**のままにすると保存済みの値がそのまま保持されるため、他のフィールドの編集で既存設定が失われることはありません。マシンの詳細カードには有効なテンプレート・上限・間隔が表示され、ログがオンのときは、ライターキューの破棄スナップショット数（非ゼロの場合）も表示されます。

## 入力ブロードキャスト

ブロードキャストは、あるペインへの入力を、登録されたペイン群（Local または保存マシンの各エンドポイントにつき 1 つ）へ同時に送り、同じコマンドを一斉に実行します。誤入力も同じように扇出されるため、仕組みは二重にゲートされています。セットは空かつ無効で始まり、セットが非空で明示的に有効化されるまで何も送信されません。

セットの管理は UI のマシンページから行えます（一覧または詳細カードで `b`、またはコマンドパレットの「broadcast input…」）。`g` でブロードキャストのオン/オフ、`a` でマシンとそのオンラインペインを順に選んで登録、`x` で選択中のターゲットを削除、`c` でセットをクリアします。セットは endpoint catalog 隣の `broadcast.json` に永続化され、CLI（`herdr broadcast status/enable/disable/add/remove/clear/send`、[CLI リファレンス](/ja/docs/cli-reference/#入力ブロードキャスト)）と共有されます。

ブロードキャスト中は、通常のターミナルモードでも mode bar に `⇄ ブロードキャスト ×N` バッジが常駐するため、知らないうちに入力が扇出されることはありません。入力したテキストとキー押下は各エンドポイントの API チャネル経由で全登録ペインに届きます。入力中のペイン自身は除外され（すでに入力を受け取っているため）、ペーストはターゲット側の bracketed-paste 処理がそのまま効き、マウス入力は一切ブロードキャストされません。入力を拒否したターゲットはトーストで一度だけ報告され、次の成功で再武装されます。オフラインのターゲットはスキップされます。同じオーバーレイで再度 `g` を押すか、`herdr broadcast disable` でオフにできます。

## 状態確認とワンショットコマンド

UI を開かずに済む簡単な確認用 CLI が 2 つあります:

```bash
herdr machine status "Build machine" [--json]
herdr machine exec "Build machine" -- systemctl --user status herdr
```

`machine status` はラベルまたはプロファイル ID（無効なマシンも可）を解決し、プロファイル、ライブ接続プローブ（到達不能時は構造化された失敗種別とメッセージ付き）、オンライン時のリモートサーバーバージョンとプロトコル互換性、保存済みポートフォワードルール、セッションログ設定を報告します。`machine exec` はファイル操作と同じ管理 SSH チャネルでリモートコマンドを 1 回だけ実行します。stdio はそのままターミナルに流れ、リモートの終了ステータスがそのままコマンドの終了ステータスになり、プロンプトもタイムアウトもありません。`--` 以降はすべてそのままリモートコマンドです。

## mosh を使わない理由

mosh は対話型ターミナルセッションのためのもので、サーバー側に独自のターミナルエミュレータを持ち、UDP 上で画面状態とキー入力を同期します。Herdr のリモート転送はまったく別物で、クライアントと常駐するリモート Herdr サーバーとの間で、Herdr のバイナリ wire プロトコル（長さプレフィックス付きの構造化メッセージ: リクエスト、レスポンス、イベント、フレーム）を運ぶ SSH stdio パイプです。mosh ではこれを運べません。画面同期以外の汎用バイトストリームチャネルがなく、サーバー側コンポーネントはターミナルセッションしか開始しないからです。

さらに重要な点として、mosh が提供する回復力は Herdr では別の層にすでに組み込まれています。リモート Herdr サーバーはセッション状態（ペイン、エージェント、ワークスペース）を保持し、ネットワークが切れても動き続けます。クライアントの supervisor は転送の断裂を検知し（TCP だけでなくアプリケーション層のヘルスチェックで）、バックオフ付きで再接続し、SSH の接続多重化を再利用するため再接続は軽量です。スリープからの復帰やネットワーク変更も単なる再接続です。セッションの存続は転送が切れないことに依存しません。これは mosh が素のシェルに追加する性質そのものです。その下に UDP ベースの mosh を重ねると、かえってモデルを弱めます。ホスト上の `mosh-server` バイナリと開放された UDP が必要になり、SSH のみ許可された環境ではどちらも提供されないからです。そのため転送は、リモート自動化が使う JSON API チャネルを含め、あらゆる場面で素の SSH のままです。

## 接続の問題

- **Reconnecting:** ネットワーク中断、スリープ、SSH 障害の後は、上限のある待機間隔で再試行します。対象マシンのバナーには再試行の回数と次回予定が表示され、クリック可能な操作が並びます。**retry now** は即時に試行し、**give up** はそのマシンを無効化します（machines ページから再有効化できます）。SSH 接続はアプリケーションの通信を監視し、通信がない間はヘルスチェックを行うため、切れた接続が Online のままになりません。Local はリモート用のプローブではなく、ネイティブ接続の終了や失敗を検知します。
- **Attention:** ホスト鍵の承認、認証、互換サーバーの準備など、バックグラウンドではできない操作が必要です。ほかのマシンは利用できます。サイドバーのマシン行には Attention マークが残り、クリックすると詳細カードが開き、構造化された失敗理由（DNS、タイムアウト、未知または変更されたホスト鍵、認証、リモートインストール、プロトコル）、推奨される次の手順、単独修復コマンド、再接続操作が表示されます。UI 内に回復経路がある失敗には **review** ボタンも表示されます:
  - *未知のホスト鍵* は初回信頼（TOFU）ダイアログを開き、ホスト、鍵タイプ、SHA256 フィンガープリントを表示します（失敗時に取得できなかった場合は先にスキャンします）。帯外でフィンガープリントを照合したら、**trust & remember**（`known_hosts` に記録して再接続）、**this time only**（カタログに書き込まないプロセス内 `accept-new` 上書きで一度だけ再接続）、**abort** のいずれかを選びます。
  - *変更されたホスト鍵* は強くブロックするダイアログを開き、マシンの再インストールと中間者攻撃の可能性を区別して表示します。帯外で確認したあとに限り、**remove old key & retry** が `ssh-keygen -R` で記録を削除して再接続し、新しい鍵は未知の鍵ダイアログで確認します。
  - *認証が必要* はガイドダイアログを開き、サーバーが提示した認証方式と設定済みの identity ファイルを表示します。**interactive auth** を承認すると、Herdr のインメモリ askpass チャネルで 1 回だけ対話的な試行を行います。SSH のパスワード／パスフレーズのプロンプトはマスク付きの TUI 入力ダイアログとして表示され、回答はプロンプト応答先にだけ送られ、ログ・保存・永続化はされません。パスフレーズのプロンプトでは、今後の非対話接続のために `ssh-add` で鍵をエージェントへ読み込めることも案内します。同じダイアログには、ホスト鍵の事前収集や修復コマンドのコピーという代替手段もあります。ウィザードで失敗したセットアップにも、同じ interactive auth とホスト鍵レビューの入口が表示されます。
- **保存済みマシンのファイルエラー:** カタログを読み取れない、または内容が不正な場合、現在の接続は変更しません。通知を表示して自動で読み取りを再試行します。

バックグラウンド接続がプロンプトに回答したり、サーバーのインストール、更新、再起動、ハンドオフを行ったりすることはありません。対話的な SSH 認証は、UI 内で明示的に承認された場合にだけ実行されます。デフォルトの経路は完全に非対話のまま、プロンプトを出さずに速やかに失敗します。UI 内の回復で扱えない場合は、Herdr が表示する単独接続用のコマンドを対話型ターミナルで実行してください。例:

```bash
herdr --remote workbox
```

プロファイルの接続先を使います。追加時に名前付きセッションを選んだ場合だけ、`--session <name>` も指定します。必要な確認に回答したら、クライアントを再起動して Attention の接続を再試行してください。バージョンが違うという理由だけで実行中サーバーを止めないでください。

認証に失敗したら、まず通常の SSH を確認します。パスフレーズ付きの鍵は、非対話型のバックグラウンド接続を始める前に `ssh-add` で読み込んでください。

## 設定と自動化

UI はデフォルトでクライアントのローカルテーマ、サイドバー設定、キーバインドを使います。選択中サーバーが公開するカスタムコマンドとプラグインは、そのサーバーで実行します。Herdr はローカルのプラグイン、設定、実行ファイル、シークレットを SSH ホストにコピーしません。リモートにコマンドがなければエラーを表示します。クライアント設定を編集したら UI の `reload config` を使います。[設定](/ja/docs/configuration/)を参照してください。

複数のマシンがある場合、デフォルトの Agent 行に `machine` トークンを表示します。既存のカスタム行は維持されるため、ラベルが必要なら `machine` を追加してください。[サイドバーの行レイアウト](/ja/docs/configuration/)ではマシンラベルの条件付き色も設定できます。

ワークスペース、タブ、ペインの ID とエージェント名はサーバーごとに独立しています。2 台に同じ `w1:p1` や `reviewer` が存在する場合があります。UI でマシンを選んでも、既存ペイン内の CLI は継承したセッションとソケットを使い続けます。リモート自動化では `herdr --machine <label-or-id> agent list` で ID を取得し、操作時にも同じプレフィックスを指定します。CLI は保存済みプロファイルの SSH 接続先とセッションを直接使うため、TUI を開く必要はありません。`--machine` を省略した場合の動作は変わりません。対応コマンド、更新要件、パスの扱いは [CLI リファレンス](/ja/docs/cli-reference/#保存済み-ssh-マシン) を参照してください。

## 更新と保存データ

保存するのは、不透明な ID、ラベル、SSH 接続先、明示的なリモートセッション名、有効状態に加え、任意の組織メタデータ（グループ、タグ、色）、SSH 接続オプション（ポート、ユーザー、認証鍵ファイル、プロキシジャンプなど）、ポートフォワードのルール、セッションログの設定です。パスワード、秘密鍵、エージェントのチケット、SSH 制御ソケットはカタログに保存しません。認証は OpenSSH が扱います。

クライアントとサーバーは同一バージョンを要求せず、互換性を合意します。保存済みマシンへの接続には、サーバーの `surface_interest` と `health_check` 能力も必要です。未対応の古いサーバーは、単独接続できても明示的に更新するまで Attention になります。そのほかの未対応メソッドは、該当する操作だけを無効にします。

互換クライアントを更新しても、リモートサーバーを置き換えたりエージェントを停止したりしません。新しいサーバー機能が必要なら、そのサーバーを明示的に更新します。通常の置き換えでは、サーバーとペインのプロセスを停止する前に確認します。

ライブハンドオフは実験的なオプトイン機能です。単独接続のセットアップで対応サーバーを置き換える場合、`herdr --remote` に `--handoff` を明示的に追加できます。通常の接続や認証の修復には不要です。[更新](/ja/docs/install/)と[セッション状態と復元](/ja/docs/session-state/)で、それぞれの操作が何を維持するか確認してください。

## ページと認証の復帰

広い画面ではマシン一覧と詳細を並べ、小さい画面では一覧から詳細を開きます。認証画面から戻っても、接続先、鍵ファイル、ポート、踏み台、セッション、表示設定の下書きが残ります。確認ページはスクロールできます。

許可された対話認証はメモリ内の askpass チャネルで検査、インストール、検証、接続の引き渡しまで進みます。パスワードは保存しません。一度だけの信頼は表示済みの公開鍵を接続専用の一時 known_hosts に固定します。永続的な信頼も表示した鍵だけを保存し、`ssh -G` で実際のポート、別名、known_hosts を解決します。代理接続は同じ経路で OpenSSH の対話確認を使います。

取消はそのタスクのローカル SSH/SCP/SFTP プロセスを終了します。すでに完了したリモート書き込みは元に戻しません。古い一覧応答は表示を変更せず、各要求の完了は処理します。

Windows では `powershell -File scripts/windows_tui_compat.ps1 -ExePath target/debug/herdr.exe -Shell powershell`、PowerShell 7 は `-Shell pwsh` で確認します。WezTerm 内で `-Interactive` を付け、選択、IME、60×16、80×24、120×40、160×50 の表示を確認します。WSL はディストリビューションの既定ユーザーとログインシェルで Linux 版 Herdr を実行します。CI の ConPTY 検証とは別に、デスクトップのマウスと IME を確認してください。
