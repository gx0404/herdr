ホスト指標と移動可能な端末グループは[監視・ドック配置](/ja/docs/monitoring/)を参照してください。


Herdr は対応エージェントを自動的に検出します。公式インテグレーションは、復元のためのネイティブセッション識別、ライフサイクル状態の報告、またはその両方を追加できます。

エージェントネイティブのセッション復元、直接のライフサイクル報告、またはその両方が欲しいときにインテグレーションを使ってください。状態権威モデルの全体像は[エージェント](/ja/docs/agents/)を参照してください。

## インテグレーションをインストールする

Herdr 内で設定を開き、インテグレーションタブから `PATH` 上で見つかったエージェント向けのインテグレーションをインストールするか、コマンドを手動で実行します。このタブでは `Enter`（およびプライマリボタン）は**選択中の行だけ**をインストールします。プライマリボタンは選択行にインストールが必要なときだけ表示され、インストールまたは更新が必要な項目をまとめて入れる `a` はフッターのキーヒントに表示されます:

```bash
herdr integration install pi
herdr integration install claude
herdr integration install codex
herdr integration install kimi
herdr integration install opencode
```

インストール後は、各インテグレーションの書き込み先と警告が行の下に表示されます。長いメッセージは途中で切れずにパネル幅で折り返され、リストはマウスホイールまたは `↑`/`↓` でスクロールできます。行をクリックするとその行が選択されます。

## ペインのレポート元

Herdr は組み込み連携のレポート（`source` が `herdr:` で始まるもの）のプロセスを確認します。ペインのプロセスツリー内からのレポートは受け入れます。`HERDR_PANE_ID` を継承しただけでツリーから離れたバックグラウンドセッションやデーモンには成功応答を返しますが、ペインの状態、セッション情報、アクティビティ、メタデータは変更しません。サードパーティーのペインレポートは従来どおりです。

tmux や screen では、送信プロセスの祖先にそのサーバーがあり、対象ペインのツリー内に同種のクライアントがあれば受け入れます。これはプロセス名による推定で、クライアントとサーバーが同一セッションに属することまでは確認しません。接続元 PID や親プロセス列を取得できない場合は受け入れます。Windows で終了した親の PID が残る孤児プロセスも、確認できない場合があります。

確認は既定で有効です。無効にするには以下を設定し、設定を再読み込みします。

```toml
[server]
verify_report_process = false
```

`HERDR_REPORT_BG_SESSIONS=1` は Claude フック側のバックグラウンドセッション除外のみを解除します。サーバー側の確認は引き続き適用され、ツリー外からのレポートを許可するには `server.verify_report_process = false` も必要です。

継承されたペイン環境による意図しないレポートを防ぐ機能であり、認証境界ではありません。独自の連携には固有で安定した source 名を使用してください。

## インテグレーションをアンインストールする

```bash
herdr integration uninstall pi
herdr integration uninstall claude
herdr integration uninstall codex
herdr integration uninstall kimi
herdr integration uninstall opencode
```

Herdr は Linux/macOS の統合設定と全プラットフォームの新規ファイルをアトミックに保存し、Windows の既存ファイルは権限を維持するため、バックアップ後に同じファイルを更新します。Windows でバックアップが通知された場合は、再試行前にエージェントを終了して設定を確認し、未完了の `.herdr-backup.pending` は復旧元に使わず設定が正しいことを確認してから削除するか、必要なら完成済みの `.herdr-backup` の内容を既存ファイルに書き戻し（ファイルがない場合は先に意図した権限を設定）、設定が正しいことを確認してからバックアップを削除してください。

## Herdr がインテグレーションをどう使うか

どのインテグレーションも、エージェントが今どのセッションにいるかを Herdr に伝えるので、サーバーの再起動後に Herdr がそのセッションを resume できます。`[session] resume_agents_on_restore = false` で無効にできます。

| インテグレーションの種類 | エージェント | 効果 |
| --- | --- | --- |
| ライフサイクル権威 | Pi、Kimi Code CLI、OpenCode | インストールされ、そのペインについて能動的に報告している間は、フックまたはプラグインのイベントが `idle`、`working`、`blocked` を決定します。同じライフサイクル権威に対して、Herdr はスクリーンマニフェストのフォールバックを併用しません。 |
| セッション識別 | Claude Code、Codex | インテグレーションは復元用のネイティブセッション参照を報告します。Claude Code はスクリーンマニフェスト検出を使います。Codex はターンフック（`--no-daemon`）、0.163 以降の OSC 7501、表示中のブロッカーを補う画面ルールを組み合わせます。 |

インテグレーションは、エージェントがあなたに求めていることの詳細も報告します（`pane.report_agent_attention`）。待っている間の質問や権限リクエスト、そしてターンが失敗した理由です。詳細は、どちらが状態を決めるかを変えません。質問はペインが `blocked` の間だけ表示されます。Claude Code は画面検出でこの状態を判定し、Codex は利用できる場合に OSC 7501 も使います。失敗は、ペインを見るかエージェントが再び作業を始めるまで残ります。Herdr での表示は[エージェント](/ja/docs/agents/)を参照してください。Claude Code（インテグレーションバージョン `12`）は権限リクエスト、質問、MCP の入力フォームを、Codex（`10`）は承認リクエストを、Kimi Code CLI（`9`）、OpenCode（`14`）、Pi（`11`）は失敗したターンを報告します。これらのバージョンから、Claude Code、Codex、Kimi Code CLI の Windows フックも、macOS と Linux のフックが送るアクティビティシグナルを `herdr pane report-agent-activity` で送ります。

エージェントネイティブのセッション復元には最新の Herdr インテグレーションが必要です: Pi インテグレーションはバージョン `2`、OMP は `3`、Claude Code は `6`、Codex は `5`、GitHub Copilot CLI は `2`、Devin CLI は `2`、Droid は `2`、Kimi Code CLI は `3`、Qoder CLI は `2`、Qwen Code は `1`、Letta Code は `1`、Cursor Agent CLI は `1`、Grok CLI は `2`、OpenCode は `5`、Kilo Code CLI は `1`、Hermes Agent は `5`、MastraCode は `1`、Antigravity CLI は `1` です。インストール済みバージョンは `herdr integration status` で確認してください。

## 独自エージェントを統合する

Herdr ペイン内で動くエージェントは、`HERDR_ENV`、`HERDR_PANE_ID`、`HERDR_BIN_PATH`、`HERDR_SOCKET_PATH` を継承します。エージェントがライフサイクルフックを提供している場合は、そのフックから Herdr の CLI を使ってセマンティックな状態を報告します:

```bash
"$HERDR_BIN_PATH" pane report-agent "$HERDR_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent \
  --state working
```

エージェントが入力待ちになったら `idle`、ユーザーの判断が必要になったら `blocked` を報告します。ブロックの説明には `--message` を使います。エージェントの終了時には、同じ source のライフサイクル権威を解放します:

```bash
"$HERDR_BIN_PATH" pane release-agent "$HERDR_PANE_ID" \
  --source custom:my-agent \
  --agent my-agent
```

Herdr の外では何もしないように、`HERDR_ENV=1` で必要な変数が存在するときだけ報告してください。`--source` はインテグレーションごとに一意かつ固定にします。報告が順不同で届く可能性がある場合は、単調増加する `--seq` を含めてください。Herdr は同じ source から届いた古いシーケンス番号を無視します。

`report-agent` に `--agent-session-id` または `--agent-session-path` を含めることも、セッション識別が状態とは独立して変わる場合に `pane report-agent-session` を使うこともできます。Herdr はその参照をペイン API とエージェント API で公開します。セッションの自動復元には、それに加えて、そのエージェントの起動方法と参照先セッションの再開方法を Herdr が把握している必要があります。

移植可能なインテグレーションには `HERDR_BIN_PATH` と CLI ラッパーを使ってください。直接 IPC が必要なコードでは、[Socket API](/ja/docs/socket-api/) に記載された同等の `pane.report_agent`、`pane.report_agent_session`、`pane.release_agent` リクエストを送信できます。

[Prime Agent の組み込み Herdr レポーター](https://github.com/PrimeIntellect-ai/prime-agent/blob/main/packages/coding-agent/src/core/extensions/builtin/herdr-agent-state.ts)は実際の実装例です。Herdr 内でのみ有効になり、エージェントイベントを `working`、`idle`、`blocked` に対応付け、セッションをまたいで報告順序を維持し、終了時に権威を解放します。

一部のインテグレーションは、エージェントのネイティブセッション参照を報告します。Herdr は公式のセッション参照を使って、`[session] resume_agents_on_restore = false` で無効化されていない限り、Herdr サーバーの再起動後に Claude Code、Codex、Kimi Code CLI、Pi、OpenCode のペインを resume します。

エージェントネイティブのセッション復元には最新の Herdr インテグレーションが必要です: Pi インテグレーションはバージョン `2`、Claude Code は `6`、Codex は `5`、Kimi Code CLI は `3`、OpenCode は `5` です。インストール済みバージョンは `herdr integration status` で確認してください。

## Pi

Pi インテグレーションをインストールします:

```bash
herdr integration install pi
```

Herdr はバンドルされた拡張を次の場所に書き込みます:

```text
~/.pi/agent/extensions/herdr-agent-state.ts
```

`PI_CODING_AGENT_DIR` が設定されている場合は、代わりに `$PI_CODING_AGENT_DIR/extensions/herdr-agent-state.ts` に書き込みます。Pi の agent ディレクトリが存在する場合、Herdr は extensions ディレクトリを作成します。アンインストールはその拡張ファイルだけを削除します。

インテグレーションバージョン `10` から、拡張は対話型（TUI）セッションでサブエージェントページ用のアクティビティツリーも報告します。Pi にはサブエージェント、Todo、バックグラウンドジョブが組み込まれておらず、拡張がそれらを提供します。Pi の組み込みツール以外のツール呼び出しはそれぞれアクティビティ項目になり、そのツールのストリーム出力が内容になります。公式の `subagent` 拡張は委任したエージェントごとに子項目を 1 つ追加します。ツリーに残るのはツール呼び出しの項目 8 個まで（新しい項目が来ると終了済みのものから削除）、各項目の下の子項目 8 個まで、各項目の出力の末尾 2,000 文字までです。Pi はこれらをディスクに残さないため、拡張はツリー全体を Herdr に送ります。アップグレード後に Pi インテグレーションを再インストールすると有効になります。

インテグレーションバージョン `11` から、実行が落ち着いた時点で最後のターンがエラーで終わっていた場合、拡張は `idle` を報告する前に Pi のエラーメッセージとともに失敗を報告します。そのため Herdr はそれを完了ではなく失敗した実行として通知します。Escape で止めた実行や、再試行で回復した実行は失敗ではありません。

## Claude Code

Claude Code フックをインストールします:

```bash
herdr integration install claude
```

このフックは、セッション開始時に Claude Code のセッション識別をローカルの Herdr ソケットに報告します。Claude Code の状態は Herdr のスクリーンマニフェスト検出から得られます。

Claude 統合 v10 は、文書化された `SessionStart` の source 値 `startup`、`resume`、`clear`、`compact`、`fork` のみに一致します。これにより、ほかの Claude 互換フックを無効にせずに、Claude フックをインポートするサードパーティ製ツールがほかの source 値でインポートされた Herdr の Claude フックを起動するのを防ぎます。アップグレード後に Claude 統合を再インストールして、従来のワイルドカードマッチャーを移行してください。Claude に新しい source 値が追加された場合は、統合の更新が必要です。

Claude インテグレーション v11 は、`SubagentStart` と `SubagentStop`(マッチャー `*`)、および `TaskCompleted` も購読します。これらのフックは、Claude Code のサブエージェントまたはタスクが変化したことをローカルの Herdr ソケットに通知するだけで、エージェントの状態は報告しません。v11 は、`TaskCreated` とともに macOS と Linux にだけインストールしていました。v12 からは Windows にもインストールされ、PowerShell フックが `herdr pane report-agent-activity` で送ります。Claude Code はこれらをバックグラウンドで実行し(`"async": true`)、終了を待ちません。v12 は `TaskCreated` を購読しなくなりました。Claude Code にこのイベントがあるのは 2.1.84 からで、それより古い Claude Code は、知らないフックイベントが `settings.json` にあると、あなた自身の設定も含めてファイル全体を無視します。インテグレーションを更新するとこのエントリは削除されます。アップグレード後に Claude インテグレーションを再インストールして追加してください。

Claude インテグレーション v12 は、あなたを待っているプロンプトが何についてのものかも報告します。`PermissionRequest` フックはツールと入力の 1 行の要約(例: `Bash: cargo test`)を、`AskUserQuestion` では質問とその選択肢を報告します。`Notification` フックは `permission_prompt` と `elicitation_dialog` の通知のメッセージを報告します。どちらもバックグラウンドで実行され、プロンプトに答えることはありません。Claude Code はこれらの通知を入力のない状態が 6 秒続いてから送り、権限の通知はツール名しか示さないため、直前 10 分以内の権限リクエストの詳細を置き換えません。詳細はペインの表示を補うだけです。Claude Code の状態は引き続き画面検出から得られ、詳細はペインが `blocked` の間だけ表示されます。Herdr は `StopFailure`(Claude Code 2.1.78 から)を購読しないため、Claude Code の失敗はフックからは届きません。

Claude Code のバックグラウンドセッション(`claude --bg` で起動したセッション、または Claude Code デーモンがホストするセッション)は Herdr に報告しません。これらはデーモンを起動したペインの変数を引き継ぐため、報告するとそのペインのエージェントとして表示されてしまいます。フックは、デーモンが設定する `CLAUDE_JOB_DIR` または `CLAUDE_CODE_SESSION_KIND=bg` 変数でバックグラウンドセッションを識別します。それでも報告させるには、その環境で `HERDR_REPORT_BG_SESSIONS=1` を設定してください。Herdr は新しいペインの環境からこの 2 つの変数を取り除くため、Herdr サーバーがバックグラウンドセッションから起動された場合でも、ペイン内の Claude Code は報告します。

Herdr は Claude Code 自身のセッションファイルからアクティビティツリーを構築します。Claude Code がバックグラウンドで実行するサブエージェントは、起動したエージェントに向けた完了通知を Claude Code が記録した時点で完了または失敗と表示されます。停止されたサブエージェントは失敗と表示され、概要の先頭に `stopped` と示されます。完了したサブエージェントが再開されると、再び実行中として扱われます。Claude Code のワークフローが実行するサブエージェントは、そのワークフローとフェーズの下にまとめられ、状態は代わりにワークフローのジャーナルに従います。結果が記録されたものは完了、失敗が記録されたものは失敗と表示され、開始だけが記録されたものはトランスクリプトが 30 分間変化しなくなるまで実行中、その後は不明と表示されます。ワークフロー自体が終了すると、その下でまだ実行中または不明のサブエージェントはワークフローの最終状態になります。こうした記録のないその他のサブエージェントは、トランスクリプトが直近 2 分以内に変化していれば実行中、それ以降は不明と表示されます。非常に長いセッションでは、Herdr はメインのトランスクリプトの新しい部分だけから完了通知を探すため、かなり前のバックグラウンドのサブエージェントは不明と表示されることがあります。

サブエージェントページでは、Claude Code のサブエージェントの出力に、各ツール呼び出しの主な引数(Bash のコマンド、ファイルパス、検索語など)が添えられます。各ツール結果は出力の先頭 5 行を表示し、残りは行数だけを示します。失敗したツール結果には `[tool error]` と表示されます。

Herdr はデフォルトで `~/.claude` を使い、`CLAUDE_CONFIG_DIR` が設定されていればそちらを使います。Claude の設定ディレクトリはあらかじめ存在している必要があります。インストールは `hooks/herdr-agent-state.sh`(Windows では `hooks/herdr-agent-state.ps1`)を書き込み、`settings.json` に Herdr のフックエントリを追加します。アンインストールは一致するフックエントリを削除し、フックスクリプトを削除します。

## Codex

Codex フックをインストールします（Codex `0.150.0` 以降が必要です）:

```bash
herdr integration install codex
```

インストール時に `codex --version` を確認します。古すぎるバージョンではインストールを拒否し、バージョンを判定できない場合は警告して続行します。

Codex を `--no-daemon` で実行すると、フックは Herdr のローカル socket API を通じてセッション識別とターンの開始・終了状態を報告します。画面ルールは表示中のブロッカーや他のシグナルの不足を補います。共有 Codex daemon はフックを別のペインへ送る場合があるため、確実な報告には `--no-daemon` を使ってください。自動起動を無効にするだけでは既存の daemon は停止しません。

Codex 0.163 以降では、Herdr はプログラム状態シグナル `ESC ] 7501 ; state=…:app=codex ST` も検出入力として収集します。`blocked` は入力待ち、`working` は作業中を示し、`idle`/`done`/`error` はアイドルの根拠になります。`state=clear` は保持中のシグナルを消去します。`app=codex` を含むシグナルだけが使われ、旧版 Codex ではタイトルと画面ルールにフォールバックします。Windows のシステム ConPTY と Herdr 同梱の ConPTY 1.24 は、どちらもこのシグナルをそのまま転送します。

Codex インテグレーション v9 は `SubagentStart` と `SubagentStop` も購読します。これらのフックは、Codex のサブエージェントスレッドが開始または終了したことをローカルの Herdr ソケットに通知するだけで、エージェントの状態は報告しません。Herdr はアクティビティツリーを Codex 自身のセッションファイルから再構築します。Codex 0.163 ではフックが既定で有効です。Herdr は旧バージョンとの互換性のため `[features] hooks = true` を明示的に書き込みます。明示的に false を指定するとフックは無効になります。v10 からはアクティビティフックが Windows にもインストールされ、PowerShell フックが `herdr pane report-agent-activity` で送ります。アップグレード後に Codex インテグレーションを再インストールして追加してください。

Herdr はすべてのプラットフォームで同じフックをインストールします:

| イベント | アクション | タイムアウト（秒） | バックグラウンド実行（`"async": true`） |
| --- | --- | --- | --- |
| `SessionStart` | `session` | 10 | いいえ |
| `UserPromptSubmit` | `working` | 10 | いいえ |
| `Stop` | `idle` | 10 | いいえ |
| `Interrupt` | `idle` | 3 | いいえ |
| `PermissionRequest` | `attention` | 10 | はい |
| `SubagentStart` | `activity` | 10 | はい |
| `SubagentStop` | `activity` | 10 | はい |

再インストールや更新では、一致する既存エントリを位置を保ったまま更新し、不足するエントリを末尾に追加します。

Codex インテグレーション v10 は `PermissionRequest` も購読します。Codex が承認を求めると、フックはツールと 1 行の要約（例: `Bash: cargo test` や `apply_patch` の対象ファイル）を、Codex が理由を示した場合はその理由とともに報告します。承認に答えたりペインの状態を決めたりすることはなく、詳細はペインが `blocked` の間だけ表示されます。承認の詳細とサブエージェントのアクティビティフックはバックグラウンドで実行されるため、Codex は完了を待ちません。

Codex のサブエージェントは「ニックネーム · タスク名」で表示されます。タスク名はエージェントパスの最後の部分で、例えば `Boyle · herdr_probe` のようになります。概要は、実行中は最後のツール呼び出し、完了後は最後の返信の先頭行、失敗や中断時はその理由を表示します。該当する概要がなければ完全なエージェントパスを使います。ニックネームのないサブエージェントはタスク名だけを表示します。

サブエージェントページでは、Codex のサブエージェントの出力は自身のスレッドの読みやすいトランスクリプトになります。`user:` とアシスタントのメッセージ、`(thinking)` の印、主な引数付きのツール呼び出しとその出力の先頭 5 行、プラン、そのターンの最後のメッセージを添えた `[task complete]` が表示されます。ツール名は名前空間を保ち、MCP は `mcp__server__tool`、他の名前空間は `ns.name`、`multi_agent_v1` と `collaboration` は名前だけを表示します。エージェント間メッセージは `[message from A → B]` に本文を続け、暗号化された内容は `(encrypted)` と表示します。開発者向けの指示、親から引き継いだ履歴、トークン数、レート制限、`security_risk_score`、`retained_context`、`additional_tools` などの内部記録は表示せず、認識できない記録は種類だけを角かっこで示します。

他のエージェントにメッセージを送る、または管理するツールの呼び出し（`send_message`、`followup_task`、`send_input`、`interrupt_agent`、`close_agent`、`resume_agent`、`wait_agent`）は、`→` の後に対象を示し、利用できるメッセージ本文を続けます。`spawn_agent` の概要は `task_name` を優先し、なければ `message` の先頭行または `items` の最初のテキストブロックを使い、値があれば ` · agent_type` と ` · model` を追加します。

Codex は信頼済みのフックだけを実行します。信頼ハッシュには `timeout` と `async` が含まれるため、上記のフックを更新した後は、次回の Codex 起動時の「Hooks need review」で再び信頼する必要があります。新規インストールでも確認が必要です。「Trust all and continue」を選ぶか、「Review hooks」を開いて Herdr のフックを信頼してください。「Continue without trusting」を選ぶと Herdr のフックは実行されず、セッション識別やフックのアクティビティシグナルを受け取れません。Codex が現在の Herdr フックをまだ信頼していない間は、`herdr integration install codex` がこの案内を出力し、`herdr integration status` も Codex の行の下に注記を表示します。Codex の `/hooks` で Herdr のフックを無効にした場合も、どちらのコマンドもその旨を表示します。信頼確認には `Interrupt` も含まれます。

Herdr はデフォルトで `~/.codex` を使い、`CODEX_HOME` が設定されていればそちらを使います。Codex の設定ディレクトリはあらかじめ存在している必要があります。インストールは `herdr-agent-state.sh`(Windows では `herdr-agent-state.ps1`)を書き込み、`hooks.json` を更新し、`config.toml` に `[features] hooks = true` があることを保証します。非推奨のトップレベル `codex_hooks` フラグが存在すれば削除もします。アンインストールは `hooks.json` から Herdr のエントリを削除してフックスクリプトを削除しますが、`config.toml` は変更しません。

セッションフックはセッション ID と Codex のトランスクリプトパスを転送し、報告後はペイン内だけの `CODEX_HOME` にもアクティビティ検出が追従します。同じ設定ディレクトリに統合をインストールし、Codex を再起動して更新済みフックを読み込んでください。再開は引き続きセッション ID を使います。アーカイブ配置と上限付き圧縮ログ対応は[Agent activity](/ja/socket-api/#エージェントアクティビティ)を参照してください。

Herdr は管理対象の Codex 起動とセッション復元を、ペイン内のランチャー経由で実行します。対話起動、`resume`、`fork` では、ペインの現在の `PATH` から実行ファイルを選び、`--help` で完全な `--no-daemon` フラグの対応を確認した場合だけ追加します。Codex 0.163 は通常 daemon を共有します。フォアグラウンド実行ではフックが現在のペインのプロセスツリー内に残り、別のペインの環境を再利用しません。保存する復元コマンドは元の `codex resume <id>` のままです。Herdr は Codex 設定を変更せず、既存の daemon も停止しません。

新しいペインでは、専用のネイティブ `codex` shim ディレクトリも `PATH` の先頭に追加します。このパスで見つかる通常の `codex` コマンドは同じランチャーを使います。ログインスクリプト、nvm/mise の初期化、alias、shell 関数、絶対パス、外部ラッパーはこれを迂回する場合があります。その場合は、対応する Codex に明示的な `--no-daemon` を指定してください。Herdr は shell の起動ファイルを編集しません。ラッパーの再帰を防ぐため、起動プロセスの `PATH` から自身の shim ディレクトリを除去します。その他の元のパス要素の相対順序は維持されます。

Windows では、その後、実際の Codex プロセスにだけ専用の非公開 tar アダプターディレクトリを前置します。Codex の PowerShell 更新処理は、ドライブ文字やバックスラッシュを誤解釈することがある Git/MSYS tar ではなく、Windows ネイティブの `tar.exe` を使用します。ランチャー経由で起動した Codex では、内蔵の更新プロンプトにも適用されます。System32 全体の優先順位、ユーザーやシステムの `PATH`、PowerShell の実行ポリシーは変更しません。Bash/Zsh は従来の GNU `tar`、`find`、`sort` を使い続けます。ランチャーを迂回した直接起動には適用されず、起動済みの Codex は再起動が必要です。Windows tar または専用アダプターが利用できない場合、Herdr は内蔵更新が失敗する可能性を警告し、この環境調整をせずに起動します。バッチアダプターはインストーラー形式のファイルパス向けであり、任意のコマンド構文を透過的に転送するものではありません。ファイルパスに含まれるリテラルの `%NAME%` はサポートしません。

非対話サブコマンド（`exec`、`review`、`app-server`、`mcp-server`、`login`、`agents`、`queue` など）、明示的な `--remote`、既存の `--no-daemon` はそのまま渡します。未知のオプションも保守的にそのまま渡します。コマンド一覧は Codex 0.163 に基づき、非表示コマンドと別名も含みます。将来追加される裸のコマンド名は、一語のプロンプトと区別できない場合があります。Herdr が対応するまでは、実際の Codex 実行ファイルのパスから呼び出してください。フラグ非対応の旧版も変更しません。能力確認は最大 2 秒、標準出力と標準エラーの合計は 64 KiB までです。確認に失敗すると、フォアグラウンド隔離が不明であることを表示して元のコマンドを一度だけ起動します。Codex の起動失敗後に自動再試行はしません。Herdr ペイン外では引数を追加しません。このランチャーは、ペインから切り離された Codex やリモート Codex のフックに信頼されたペインの所属を付与しません。

## Kimi Code CLI

Kimi Code CLI フックをインストールします:

```bash
herdr integration install kimi
```

このフックは、ネイティブ復元と権威ある `idle`、`working`、`blocked` 状態のために、Kimi のセッション識別とライフサイクル状態を Herdr に報告します。Kimi Code CLI `0.14.0` 以上が必要です。

インテグレーションバージョン `8` からは、フックは `SubagentStart`、`SubagentStop`、`Notification`（`task.*`）、`PostToolUse`（`TodoList`）も購読します。これらのエントリはアクティビティツリーが変化した可能性があることを Herdr に伝えるだけで、セッションの内容は含みません。アクティビティツリー自体は Herdr が Kimi のセッションファイルを読んで組み立てます。

インテグレーションバージョン `8` は、Kimi のターンの終わり方をすべて `idle` に対応付けます。ターンが完了したときの `Stop`、中断したときの `Interrupt`、そしてプロバイダーのエラーや認証エラーなどでターンが失敗したときの `StopFailure` です。そのため、失敗したターンのあと Kimi が終了するまでペインが `working` のまま残ることはなくなります。Herdr がサポートするすべての Kimi Code CLI バージョンに `StopFailure` があります。アップグレード後に Kimi インテグレーションを再インストールして追加してください。

インテグレーションバージョン `9` からは、`StopFailure` はペインが `idle` になる前に、Kimi のエラー種別とメッセージとともに失敗も報告します。そのため Herdr はそれを完了ではなく失敗したターンとして通知します。

インテグレーションバージョン `8` は、フック自身の絶対 `KIMI_CODE_HOME`（未設定の場合はフックのホーム）からセッションディレクトリも報告します。サーバーと設定ディレクトリが異なっていても、各ペインのアクティビティを追跡できます。`SessionStart` がファイル作成より先に動いた場合は、後続のライフサイクルとアクティビティイベントで再検索します。セッション ID に一致する一意のディレクトリだけを受け入れ、復元には引き続き ID を使います。空値、相対パス、リテラルの `~`、重複ディレクトリ、または 256 個の作業ディレクトリエントリを超える検索ではパスを省略し、通常の状態報告を続けます。Windows でもディレクトリを補足し、バージョン `9` からはそのフックもアクティビティの通知を `herdr pane report-agent-activity` で送ります。スクリプトを更新するには Kimi インテグレーションを再インストールしてください。

Herdr はデフォルトで `~/.kimi-code` を使い、`KIMI_CODE_HOME` が設定されていればそちらを使います。Kimi Code の設定ディレクトリはあらかじめ存在している必要があります。インストールは `hooks/herdr-agent-state.sh`(Windows では `hooks/herdr-agent-state.ps1`)を書き込み、`config.toml` に Herdr 管理の `[[hooks]]` エントリを追記します。アンインストールは Herdr 管理の設定ブロックを削除し、フックスクリプトを削除します。

インストールとアンインストールは、設定や管理対象のフックファイルを変更する前に TOML と管理ブロックのマーカーを検証します。マーカーの欠落、逆順、入れ子、重複は拒否され、これらのファイルは変更されません。TOML 文字列内のマーカーに似たテキストは管理ブロックと見なさず、無関係なコメントと LF/CRLF の改行は保持します。破損した `config.toml` を修復または復元してから再試行してください。現在のインストールでは `hooks` が未定義、または `[[hooks]]` テーブル形式である必要があり、既存の `hooks = []` やインライン配列は自動変換せず拒否します。末尾に改行のないファイルにはブロックを追記するための区切り改行を補い、この改行はアンインストール後も残ります。

Herdr は保存された Kimi セッションを `kimi --session <id>` で resume します。

## OpenCode

OpenCode プラグインをインストールします:

```bash
herdr integration install opencode
```

この連携は OpenCode V1 `1.18.29` 以降と OpenCode V2（beta `19242` で検証済み）に対応します。OpenCode の設定ディレクトリはあらかじめ存在している必要があります。Herdr はサーバー側のエントリポイントを `~/.config/opencode/plugins/herdr-agent-state.js` に、共通 TUI プラグインを同じ設定ディレクトリの `herdr-tui-session.js` に、V2 TUI エントリポイントを `herdr-opencode/tui.js` にインストールします。

インストール時、V1 TUI プラグインを `tui.jsonc` に、V2 TUI プラグインを `cli.json` に登録し、他の設定やプラグインは保持します。`tui.json` に既存の V1 登録がある場合もインストール済みとみなし、`tui.jsonc` を作成せずに再利用します。アンインストールでは、両方の TUI 設定ファイルから Herdr の登録を削除し、ファイルと他の設定は保持します。OpenCode に移行すべき V1 TUI 設定（`tui.json` または `kv.json`）が残っている場合、Herdr は初回起動時の移行を妨げないよう登録を見送ります。その場合は一度 `opencode2` を起動してから連携を再インストールしてください。それ以外の場合は Herdr が `cli.json` を作成してプラグインを登録します。インストール後は OpenCode TUI を再起動してください。アンインストールは管理対象のプラグインファイルと設定項目を削除します。

V2 のライフサイクル報告はペイン内の TUI で実行され、複数のペインが同じ OpenCode サーバーを共有する場合も、選択されたルートセッションにイベントを対応付けます。完了時または中断時に working 状態を解除し、未処理の権限要求やフォームは blocked 状態を維持します。実行失敗はエラーの詳細を報告してからペインを `idle` に戻し、`blocked` には留まりません。V2 Mini とヘッドレスクライアントは TUI プラグインを実行しないため、このライフサイクル報告は利用できません。

V1 TUI はペインで選択したセッションとその子孫を追跡します。いずれかが実行中・再試行中なら working、権限要求や質問が未処理なら blocked を維持します。接続時に既存の状態を読み込み、キャンセル済みツールの要求が再接続後に blocked を復活させることはありません。サブエージェントの閲覧では元のセッション群を維持し、子セッションへ直接接続した場合は兄弟ではなくその子孫だけを追跡します。

ローカル V1 の `opencode run` と `opencode --mini` は従来のサーバーフックを維持します。この変更は Mini やヘッドレスクライアントにペイン固有のライフサイクル報告を追加するものではありません。連携の更新後は TUI と共有 OpenCode サーバーの両方を再起動し、古いサーバー報告がペインの状態を上書きしないようにしてください。

OpenCode V1 では、サーバープラグインは OpenCode 自身がセッションを busy と報告している間（`session.status`）だけ `working` を報告し、OpenCode がイベントを発行した順に報告を送ります。そのため、ターンが終わるとペインは必ず `idle` に戻ります。ほかのプラグインがターンを開始せずにメッセージだけを追加した場合（`noReply` のプロンプト、たとえばバックグラウンドタスクの通知）、ペインの状態は変わりません。

このプラグインは、OpenCode が Herdr のペイン内で動いている間、ライフサイクル状態とセッション識別を報告します。OpenCode がセッション情報を含むイベントを発行した後、Herdr は報告されたセッション id を使って `opencode --session <id>` でペインを resume できます。プラグインがインストールされていないときは、スクリーンマニフェスト検出が引き続き利用できます。

インテグレーションバージョン `13` から、V1 のサーバープラグインはセッションまたはその Todo が変わったとき（サブエージェントのセッションも含む）にも Herdr に知らせます。V2 の TUI プラグインはこの通知を送りません。この通知にセッションの内容は含まれません。アクティビティツリーは Herdr 自身が `opencode db` で読み取り専用に取得し、そのセッションが開始したサブエージェントのセッション（それぞれのメッセージとツール呼び出しが内容になります）と、セッションの Todo から構成します。最後の応答がエラーで終わったサブエージェントのセッションは失敗と表示され、概要の先頭にエラー名と説明が示されます(例: `APIError: Rate limit exceeded`)。OpenCode はすべてのエラーを保存するわけではありません。設定されたモデルが存在しなくなった場合は自身の画面にだけエラーを表示し、セッションにはプロンプトしか残らないため、Herdr はそのサブエージェントを最終更新から 30 分間は実行中、その後は不明と表示します。

インテグレーションバージョン `14` から、`opencode run` と `opencode --mini` が使う V1 のサーバープラグインは、セッションのエラーを失敗したターンとして、エラー名と説明とともに、そのターンを終える `idle` の直前に報告し、エラーを `blocked` として報告しなくなります。OpenCode はエラーの直後にセッションをアイドルにし、ユーザーを待っているものはないためです。ターンが回復するエラー(OpenCode がコンテキストを圧縮して続行するコンテキストオーバーフローなど)と、中断されたターン(`MessageAbortedError`)は失敗ではありません。V1 TUI も選択したルートに対してエラー詳細を idle より先に報告します。V2 TUI は `session.execution.failed` の構造化エラーを `idle` の前に報告します。どちらもルートの失敗時に古い要求を消去し、セッション選択と破棄後のガードを維持し、別のルートや子セッションの失敗を選択中のルートの失敗として扱いません。バージョンは既存の `14` のままです。管理ファイルを更新するには連携を再インストールして TUI を再起動してください。イベント契約は OpenCode のソースと合成テストで確認しましたが、この変更は実際の OpenCode インストールでまだ smoke 検証していません。

## 廃止されたインテグレーション

この fork が提供する公式インテグレーションは Pi、Claude Code、Codex、Kimi Code CLI、OpenCode の 5 つだけです。それ以外の組み込みインテグレーションは、同梱の検出マニフェストとともに廃止されました。

- CLI は廃止された名前を受け付けません。`cursor` や `omp` のような廃止済みの名前に対して、`herdr integration install` と `herdr integration uninstall` は廃止の通知と現在サポートされるターゲットの一覧を返し、`herdr integration status` にも表示されません。以前の実験的な `letta` ターゲットは API 上の名前を持たなかったため、代わりに未知のターゲットのエラーと同じ一覧が返ります。
- 古いクライアントは、廃止されたターゲットを `integration.install` や `integration.uninstall` の API メソッドへ送ることがあります。リクエストは従来どおり解析され、`integration_retired` エラーが返ります。`integration.list` は廃止されたターゲットを返しません。
- 以前のビルドが廃止済みエージェントの設定ディレクトリに書き込んだフックやプラグインには手を加えません。不要になったら手動で削除してください。それらが報告するセッションは非公式ソースとして扱われ、復元には使われません。`herdr integration uninstall` も廃止済みの名前を拒否するため、この fork はそれらを代わりに削除できません。そのエージェント自身のドキュメントでフックやプラグインファイルの正確な場所を確認し、設定ディレクトリを自分で開いて削除してください。
- ペインで動く廃止済みエージェントは通常のプログラムとして扱われます。自動検出はされず、それを指す設定キー（`[ui.sound.agents]` の上書きなど）は無視されます。

廃止の有無にかかわらず、どのエージェントも[独自エージェントを統合する](#独自エージェントを統合する)の汎用インターフェースで状態を報告できます。ZCode は組み込みインテグレーションではなく、外部エージェントソースとしてサポートされます。ペインの中では決して動かないデスクトップアプリなので、Herdr は最近の実行中セッションを Sessions サイドバーの External グループに表示します（[エージェント](/ja/docs/concepts/#エージェント)を参照）。ZCode には何もインストールしません。

## 削除されたアカウント使用量の監視

この fork は CLI や AI アカウントの使用量を追跡しなくなりました。Monitor パネルの Accounts ページ、Agent 行の使用量カード、**Usage** と **Bind account** のメニュー項目、`herdr api usage-report`、`account.usage.*` と `account.binding.set` のソケットメソッドは削除されています。ホストの監視は変わりません（[監視・ドック配置](/ja/docs/monitoring/)を参照）。

- 以前のビルドで Claude Code の公式ステータスラインコールバックを有効にしていた場合、Claude Code の `settings.json` にある `statusLine` コマンドは、自分のステータスラインコマンドの前で今も `herdr api usage-report` を実行します。Claude インテグレーション v12 はこのラッパーを取り除き、元のステータスラインに戻します。`herdr integration install claude` を実行するか、Herdr がインテグレーションの更新が必要だと知らせたときに更新してください。Claude インテグレーションをアンインストールしてもラッパーは取り除かれます。
- Pi インテグレーションバージョン `11` はセッションの使用量を送らなくなりました。`herdr integration install pi` で更新してください。
- 以前のビルドが Antigravity CLI の `~/.gemini/antigravity-cli/settings.json` でステータスラインに付けたラッパーを、Herdr はもう削除しません。そこにある元の `statusLine` コマンドを手動で戻してください。
- 設定ファイルの `[account_usage]` セクション（`[[account_usage.accounts]]` エントリを含む）は、設定の警告を出したうえで無視されます。削除すると警告は出なくなります。

## カスタムステータスラベル

インテグレーションは、ライフサイクル状態を意味的な状態としてのみ報告します。たとえば、ライフサイクル報告に表示フィールドを加えず、エージェントを `working` として報告します。

```bash
herdr pane report-agent w1:p1 \
  --source custom:docs \
  --agent docs-bot \
  --state working
```

Herdr 管理のインテグレーションと並走するユーザーフックは、`report-agent` ではなくメタデータを使うべきです。メタデータは、インテグレーションの `idle`、`working`、`blocked` やセッション復元の権威を奪わずに表示を変えます。`--agent` と `--applies-to-source` は表示フィールド (`--title`、`--display-agent`、`--state-label`) だけを保護します。トークンパッチは常に適用され、クリアまたは TTL の更新は報告側が管理します。`--display-agent` は表示名を変更します。

```bash
herdr pane report-metadata "$HERDR_PANE_ID" \
  --source user:claude-title \
  --agent claude \
  --title "Refactor auth middleware" \
  --display-agent "Claude: auth" \
  --token summary="refactor auth" \
  --state-label working="refactoring auth" \
  --ttl-ms 3600000
```

トークンと状態ラベルは表示専用です。wait、通知、ワークスペースのロールアップは引き続き意味的な状態を使います。

## インテグレーション状態のデバッグ

既知のエージェントを一覧します:

```bash
herdr agent list
```

Herdr に何が見えているか確認する必要があるときはペインを読みます:

```bash
herdr pane read w1:p1 --source recent --lines 50
```

インテグレーションの状態がおかしく見えるときは、まずエージェントが Herdr 内で動いていること、そして該当のフックまたはプラグインが同じユーザーアカウントにインストールされていることを確認してください。
