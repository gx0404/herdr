Windows 原生支持已正式发布。

Windows 上的 Herdr 使用 ConPTY 和 Windows 的进程/运行时行为,而不是 Herdr 最初围绕构建的 Unix PTY 模型。大多数核心工作流已受支持,但部分能力与 Linux/macOS 不同或取决于平台。随着这些剩余差距逐步缩小,Windows 可能会收到更多平台专用修复。

使用 PowerShell 在 Windows 上原生安装 Herdr:

```powershell
powershell -ExecutionPolicy Bypass -c "irm https://herdr.dev/install.ps1 | iex"
```

如果端点安全软件阻止该无文件 PowerShell 命令，请打开命令提示符并运行：

```cmd
curl.exe -fsSLo install.cmd https://herdr.dev/install.cmd && install.cmd && del install.cmd
```

Windows 构建同时通过稳定版和预览版更新通道提供。新安装默认使用稳定版,常规使用也建议选择稳定版。现有预览安装会继续留在预览通道,直到你运行 `herdr channel set stable`。如果旧预览构建拒绝该命令,请先在预览通道运行一次 `herdr update`,再重试。预览版会提供来自 `master` 的更新、测试较少的修复,也可能出现回归;只有在接受这一取舍时,才应通过 `herdr channel set preview` 主动启用。

安装器将发布版本保存在 `%USERPROFILE%\.herdr\packages\standalone\releases` 下,把当前带版本号的发布目录加入 PATH,将 `%LOCALAPPDATA%\Programs\Herdr\bin` 保留为稳定的兼容别名,并保留少量旧版本,以免运行中的进程阻塞更新。

对于内部测试,`HERDR_MANIFEST_URL` 可以让安装器指向自定义清单,而不是 Herdr 的稳定或预览清单。使用自定义预览清单时还应设置 `HERDR_CHANNEL=preview`。

本地持久会话会在客户端分离或终端窗口关闭后继续运行。通过 Windows OpenSSH 启动的服务器和窗格进程也会在注销后继续运行;再次运行 `herdr` 即可重新连接。

本地服务器与客户端连接支持深层嵌套的会话目录。Herdr 先规范化命名管道路径，再用 Windows 长路径形式打开；不会迁移会话数据，也不改变 CLI 报告的 socket 路径。既有短路径连接保持兼容。文件系统权限、单个目录组件的长度限制，以及窗格内程序自身的路径支持限制仍然适用。

以管理员权限启动的 Windows 服务器默认只接受管理员客户端，包括通过已提权的 SSH 登录启动的服务器。普通服务器接受同一账户的普通和管理员终端客户端；连接不会改变服务器的权限。

如果确实要向普通客户端开放管理员会话，请设置：

```toml
[server]
allow_unelevated_clients = true
```

此设置仅作用于 Windows，默认关闭，在新服务器启动时生效，包括自动启动。重载配置不会改变运行中服务器的访问策略。也可以在管理员终端使用 `herdr server --allow-unelevated-clients`，仅为一个服务器进程启用共享；命名会话使用 `herdr --session <name> server --allow-unelevated-clients`。即使配置值为 false，此标志也会启用共享。

两种方式都会允许同一账户的普通本地进程控制管理员窗格，其他账户仍被排除。除非配置已启用共享，否则重启后需要再次传入该标志。既有服务器保留原访问策略，直到停止并用更新后的构建重启；停止会关闭其窗格。配置与恢复文件仍使用基于账户的权限。

关闭窗格会结束从它启动的程序。关闭窗格的 ConPTY 会向控制台程序发送关闭事件;短暂宽限后,Herdr 会终止窗格进程树里剩下的所有进程,包括从窗格启动的图形界面程序,例如 `start notepad`。Windows 没有 Unix 会话,所以 Herdr 从窗格 shell 沿子进程找出这棵树,并核对进程启动时间,被复用的进程 ID 不会把无关程序卷进来。启动器已经退出的程序与窗格不再关联,会继续运行。Herdr 自己的后台服务器不受影响:在窗格里由 `herdr` 命令启动的服务器会连同它的全部会话继续运行。要让程序在窗格关闭后继续运行,请在 Herdr 之外启动它,或者通过立即退出的启动器启动,例如 `cmd /c start notepad`。

Windows 智能体进程检测会扫描窗格 shell 的后代进程,识别直接运行的智能体和常见的命令包装器,包括 npm/Node 和 Git Bash 进程链。它会跨越模拟的 `exec` 边界跟踪从 Git Bash 启动的智能体,但这和 Unix 前台进程组检测不是一回事。

进程 ID 可能被复用。前台检测和进程祖先链检查会保留进程句柄，将父子关系、创建时间、可执行文件名和命令行绑定到同一个进程实例。无法核验的关系保持未知，不会把旧快照字段与新进程拼接。这不改变上报来源的授权策略或窗格终止规则。

进程扫描不占用 server 的异步工作线程,同一个检测节拍里扫描的窗格共用一份进程快照。每个进程实例(进程 ID 加创建时间)只分类一次,长期存在的 shell 辅助进程不会在每次扫描时被重新读取;读不到命令行的进程约 1 秒后会再检查一次,因为经 `node.exe` 等运行时启动的智能体只能从命令行认出。没有智能体的安静窗格大约每 2 秒重新扫描一次;窗格一有输出,下一个节拍就会扫描,所以开始绘制界面的智能体仍会和以前一样快被识别。

没有子进程的空闲 `cmd.exe`、Windows PowerShell 和 `pwsh` 窗格会在进程快照有效期间复用前台进程选择。输入转发使用异步任务，不再为每个窗格单独保留一个转发线程；排队输入仍受容量限制。新建窗格依据目标布局选择初始终端尺寸，后台标签页中的窗格也一样；窗格不会仅因被创建就分配一份完整渲染快照。

Windows 支持安装全部五家官方集成:Pi、Claude Code、Codex、OpenCode 和 Kimi Code CLI。子 agent 活动信号只在 Unix 上提供:Windows 上 Claude Code 与 Codex 集成只安装会话钩子,Kimi Code CLI 的钩子会忽略活动事件,因此这些智能体的活动树只随 Herdr 的定期刷新更新。

插件以预览状态支持在清单中声明 `windows` 平台。GitHub 安装、本地链接、构建命令、动作、事件和插件窗格在 Windows 上尽力而为。命令是 argv 命令,必须兼容 Windows;`npm`、`bun`、`node` 之类的 Node 包 shim 只要在 `PATH` 上就应该能用,而使用 `sh` 或 Bash 的 Unix 专用示例需要 Windows 专用的替代方案。平台过滤器会跳过不支持的构建命令,并对不支持的动作或窗格返回 `platform_unsupported`。

### Codex 更新器路径

原生 Windows tar 包装器支持 Codex 更新器使用的归档文件路径和输出目录中的中文字符，仅适用于恰好四个参数的形式：`-xzf archive -C output`。Herdr 用 Rust 打开归档，通过标准输入交给系统 tar，并将输出目录设为 tar 的工作目录，避免这些外部路径经过 ANSI 代码页转换。其他参数形式仍原样交给系统 tar，保留既有 CMD `%` 展开边界。这不保证归档内部 Unicode 文件名的兼容性，也不改变 GNU tar 或 Bash 的选择。

## 部分支持

| 能力 | 状态 |
| --- | --- |
| shell `cd` 之后的实时 cwd | 部分支持 |
| 通过 shell 集成/OSC7 的实时 cwd | 已支持 |
| 向本地窗格中的智能体粘贴剪贴板图像 | 取决于终端/智能体 |
| CJK 输入法候选窗口定位 | 部分支持 |
| 前缀输入源切换 (韩语输入法) | 部分支持 |
| Kitty graphics 渲染 | 取决于终端 |
| 主机光标渲染 | 部分支持 |

Herdr 可以在正确的目录中启动窗格,并能从你启动 Herdr 的目录创建初始工作区。启动之后 PowerShell 的目录变化则不同: Herdr 能检查的进程字段无法可靠跟踪后续的逻辑 `cd` 变化。实时 cwd 上报请使用 Herdr 集成或提示符 shell 集成。

使用 `herdr --remote` 时,配置的远程图像粘贴键会读取 Windows 剪贴板图像并传输到远程主机。把一个本地图像文件拖入 Windows Terminal 也会传输该文件并粘贴远程路径。

前缀输入源切换可作为针对韩语输入法的选择性实验功能使用。前缀命令处于活动状态时,它会把韩文输入切换为英文,之后再恢复先前的模式:

```toml
[experimental]
switch_ascii_input_source_in_prefix = true
```

此选项暂不支持其他 Windows 输入法。参见[配置](/zh-cn/docs/configuration/#前缀输入源切换)。

Windows 上的部分智能体可以接收 `ctrl+v` 并直接读取剪贴板图像。Herdr 自己的剪贴板图像读取器尚未接入本地原生 Windows 窗格,因此智能体原生图像粘贴仍取决于终端和智能体。`alt+v` 等智能体图像粘贴快捷键不会增加由 Herdr 管理的本地剪贴板桥。远程剪贴板图像桥通过连接 Linux/macOS/Windows 主机的 `herdr --remote` 单独受支持。

Kitty graphics 默认启用，并取决于外层终端。Herdr 会像在其他平台上一样在 Windows 上输出 Kitty graphics protocol。这个路径已在 Windows WezTerm 托管 WSL 中 Herdr 的配置下得到验证，但原生 Windows 的各种终端与 ConPTY 组合尚未全部验证。Windows Terminal 不提供 Herdr 使用的 Kitty graphics 路径。如果外层终端无法正确处理图形输出，请设置 `[terminal].kitty_graphics = false`。

## 已知注意事项

### 光标渲染

Herdr 的原生 Windows 窗格依赖 ConPTY。当前 Windows 终端的光标处理可能会在多路复用器重绘屏幕时显示中间光标位置。因此,在持续输出期间,原生光标可能闪烁、跳动,或短暂留在旧位置。这个现象也能在其他 Windows 原生终端多路复用器以及直接连续更新 VT 光标位置的压力测试中复现,所以 Herdr 无法在保留原生光标行为的同时彻底消除它。

为了优先保证视觉稳定性,默认的 `host_cursor = "auto"` 会在原生 Windows 和 WSL 上把 Herdr 光标绘制为终端单元格内容。其他 Linux 和 macOS 客户端仍使用原生终端光标。Windows 上的绘制光标稳定且不闪烁,但不会使用外层终端的原生闪烁、形状或光标颜色。

绘制光标并不是 Windows 用来定位输入法预编辑文本和候选窗口的真实光标。因此,韩语、日语或中文输入法 UI 可能显示在错误位置。如果遇到这个问题,请改用外层终端光标:

```toml
[ui]
host_cursor = "native"
```

原生模式会恢复输入法定位,但在持续输出期间可能再次出现偶发的光标闪烁、跳动或旧位置残影。这是当前 Windows 支持中的兼容性取舍。

### 键盘和鼠标

Windows 终端并不都以相同形式报告带修饰键的按键。Herdr 在 Windows Terminal 和 Windows 上的 Alacritty 中保留鼠标报告和 `ctrl+j`。原生 Windows 输入路径还会通过默认 ConPTY 窗格保留物理按键的按下、重复、释放、独立 Escape 和 `shift+enter`。带修饰键的输入仍依赖外层终端报告可区分的按键事件;如果它把 `shift+enter` 报告为普通 Enter,Herdr 也只能转发普通 Enter。

`ctrl` 加字母(不带 `alt` 或 AltGr)送到窗格时总会带上对应的控制字符,例如 `ctrl+c` 是 `0x03`,即使外层终端、按键重映射工具或输入法报告的是普通字母或没有字符。MSYS2 和 Cygwin 程序(例如 MSYS2 zsh 窗格里的 `sleep`)只根据这个字符产生 SIGINT,因此 `ctrl+c` 能像中断原生程序一样中断它们。

旧版 Windows 10 的系统 ConPTY 会丢弃 Kimi 和 Pi 等智能体使用的 Kitty 键盘协议序列，因此 Windows 包包含 Microsoft 当前的应用本地 ConPTY 运行时。仅在诊断捆绑运行时的兼容性问题时，才应在启动 Herdr 前设置 `HERDR_WINDOWS_CONPTY=system`。

初始本地客户端握手有 4 秒期限。服务器最多同时接纳 32 个握手；未完成初始 hello 的连接会被关闭，超出的尝试会在槽位释放前被拒绝。这是连接安全上限，不能通过设置调整。

客户端输出连续 30 秒没有进展时，该连接会被关闭，读写两个传输线程都会回收。成功写入会重新计算这段期限，因此慢读客户端不会仅因一帧发送超过 30 秒而断开。可靠控制消息仍限制为 4 MiB 或 4096 条排队消息；超过任一上限会中止连接，而不是无限扩队列。正常关闭会排空已接受的控制消息；服务器退出时，所有剩余客户端共享 1 秒排空窗口，未完成的连接随后中止。

观察客户端的渲染队列已满时，服务器跳过该观察者的窗格运行态访问和重绘。写端腾空通知会重新调度最新画面，即使窗格不再产生新输出也能恢复。客户端端点的大结果另行暂存，随队列余量按有界分块发送，详见 [Socket API](/zh-cn/docs/socket-api/#协议稳定性)。

## 复制与粘贴

Herdr 的窗格文本复制在 Windows 上可用。在窗格内拖选文本即可通过 Herdr 复制。

文本粘贴请在 Windows Terminal 中使用 `ctrl+shift+v`。多行文本粘贴是带括号的 (bracketed),因此 shell 和智能体提示符会把它作为一次粘贴接收,而不是逐行提交。按住 `shift` 再右键,可以使用外层终端的粘贴操作,而不把点击发给 Herdr。

分块到达的 bracketed 粘贴仍会保留 Unicode 文本和结束标记。完整粘贴超过 1 MiB 时会显示拒绝通知，但不会断开客户端；其它超限输入可能关闭连接。

## Windows 不支持

| 能力 | 状态 |
| --- | --- |
| 直接终端附加 (`herdr terminal attach`) | 不支持 |
| 实时服务器交接 | 不支持 |
| Unix 文件描述符交接 | 不支持 |
| Unix 前台进程组 | 不支持 |
| 本地原生窗格中的 Herdr 剪贴板图像桥 | 不支持 |
| 签名二进制 / 规避 SmartScreen | 不支持 |

在 Windows Terminal 中,使用与 Linux 和 macOS 相同的远程命令:

```powershell
herdr --remote workbox
```

目标主机可以运行 Linux、macOS 或 Windows。Windows 主机会复用 `PATH` 或当前有效的托管版本中的兼容软件包。交互式连接和保存机器设置会在安装或更新完整软件包前询问；后台重连只查找已安装的软件包，不会提示安装或更新。Herdr 使用已安装的 Windows OpenSSH 客户端和你的 SSH 配置。Windows OpenSSH 不使用 Herdr 的 Unix control socket 连接复用,因此建议通过 Windows `ssh-agent` 使用密钥认证,避免远程设置期间重复提示。

Windows 更新通过 Windows 安装器进行,并更新当前带版本号的发布路径。新终端和重新连接的 SSH 会话会获得该路径;在其中启动 Herdr 即可使用更新后的客户端。兼容的运行中服务器会让窗格继续运行。只有需要新版本的服务器端改动时,才稍后重启服务器。实时交接仅限 Unix。

## 报告 Windows 问题

请包含:

- Herdr 版本。
- Windows 版本。
- 终端应用。
- Shell,比如 PowerShell 或 cmd。
- 是否使用了命名的 `HERDR_SESSION`。
- 相关的 Herdr 日志。
- 精确的复现步骤。
