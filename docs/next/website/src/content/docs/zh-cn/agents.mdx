Herdr 为同时运行多个编程智能体而生。每个智能体都待在一个真实的终端窗格里,shell、日志、提示符和运行中的进程都完好无损。Herdr 跟踪哪些窗格里有智能体,把它们的状态汇总到标签页和工作区,让你直接跳到需要关注的窗格,而不是手动轮询每个终端。

[会话侧栏](/zh-cn/docs/concepts/#会话侧栏)把工作区、标签页、智能体会话、普通终端和只读外部活动组织在同一棵树中。`prefix+a` 依次在需要输入、失败、待查看的在线窗格会话之间循环，不包含离线缓存或外部条目。

要从脚本或另一个智能体协调它们,请参阅[智能体自动化](/zh-cn/docs/agent-automation/)。

智能体总览（`prefix+g`）按 **需要输入 → 失败 → 待查看 → 工作中 → 空闲** 分组。按 `g` 切到位置导航，保留机器、工作区和普通终端。Space 预览收到的洞察，包括问题、选项、失败详情、模型与位置；不会声称恢复服务端已截短的文本。Enter 跳到真实窗格。

用 `r` / `u` / `R` 在客户端标为已读、未读或全部已读。手动未读不会因查看窗格立即消失，直到你明确标为已读，或新轮次、智能体替换、服务端 boot 变化使其失效。每个客户端跨端点最多保存 256 个手动标记，不改变生命周期或失败 attention。离线缓存会话置灰，不能发送动作。

空闲或待查看会话仅在目标端点明确宣告 `agent.prompt` 时可按 `e` 打开多行回复草稿。Enter 换行，Ctrl+Enter 或「发送」确认提交，使用 `wait = None`。工作中、失败、等待权限或问题的智能体不能在此回复，应「跳转并回答」。发送单飞；错误和超时保留草稿，但不会自动重试。切换目标、boot、替换身份或关闭总览后，迟到响应不能污染当前状态。超时不能证明服务端没有提交提示，重试前应检查终端。

## 受支持的智能体

智能体获得 Herdr 支持有两种方式:由 Herdr 支持它,或由它自己支持 Herdr。无论哪种方式,你都能看到每个智能体的 `idle`、`working` 和 `blocked` 状态,在它完成或需要你处理时收到通知,并能在脚本中等待它。

其他智能体在 Herdr 窗格中照常运行,只是显示为普通终端。

### 由 Herdr 支持

Herdr 能识别这些智能体,并从它们在屏幕上绘制的内容读取状态。要在 Herdr 服务器重启后回到同一个会话,请用 `herdr integration install <name>` 安装该智能体的集成。每个集成会安装什么,见[集成](/zh-cn/docs/integrations/)。

| 智能体 | 集成 | 说明 |
| --- | --- | --- |
| Pi | 安装后为生命周期钩子;否则为屏幕清单 | 状态与会话 |
| Claude Code | 屏幕清单 | 会话 |
| Codex | 轮次钩子（`--no-daemon`）+ OSC 7501 + 屏幕规则兜底可见阻塞 | 会话 |
| OpenCode | 安装后为生命周期插件;否则为屏幕清单 | 状态与会话 |
| Kimi Code CLI | 安装后为生命周期钩子;否则为屏幕清单 | 状态与会话 |

本 fork 只检测并提供这五家的集成;其余智能体的去向见[已退役的集成](/zh-cn/docs/integrations/#已退役的集成)。不受支持的智能体仍然可以作为普通终端进程正常运行,只是在你添加集成或通过 socket API 上报状态之前,可能得不到丰富的状态。

ZCode 作为只读外部来源，仅列出近期仍在运行的根会话；没有任务运行时不显示对应的「外部」分组。会话结束后，只要未归档且仍在 72 小时近期窗口内，仍可按外部 ID 读取历史活动树。

活动树发现使用有容量上限的后台队列。读会话文件的来源(Claude Code、Codex、Kimi Code CLI,以及 Pi 上报的快照)与起查询程序的来源(OpenCode 的 `opencode db`、ZCode 的 `sqlite3`)各有自己的队列和工作线程,慢查询不会拖慢其他窗格的发现。每个窗格同时仍最多只有一次发现在途。队列满时被拒绝的刷新仍会按原有节流重试,包括空闲窗格的首次发现。ZCode 转录每次最多扫描 8 MiB,超长行分段跳过,不会把尾部片段当成新记录。续读时原样传回返回的游标;未完成的普通短行会等待结尾换行。

这些智能体会自己向 Herdr 上报状态。无需安装任何东西,在 Herdr 窗格中运行即可。

## 状态如何判定

对于由 Herdr 支持的智能体,Herdr 在每个窗格中找到智能体进程,并读取窗格的实时底部,而不是你滚动到的位置。检测清单中的规则决定该屏幕表示 `idle`、`working` 还是 `blocked`。如果集成也上报状态,Herdr 会使用这些上报,而不是读取屏幕。

对于自身支持 Herdr 的智能体,由智能体自己的上报决定状态。

当 Herdr 能确认同一个智能体进程仍存活于该窗格时，离开前台不会丢弃其会话身份、名称或生命周期钩子的状态上报权。例如，在 Unix shell 中用 `ctrl+z` 挂起后再用 `fg` 恢复，会保留同一身份。后台保留期间，Herdr 不会把前台 shell 或另一个命令的屏幕当作智能体状态来分类。确认进程退出或被另一个智能体进程取代后，旧身份才会清除；这不会新增 `suspended` API 状态。发送输入前请先恢复目标任务：窗格输入仍交给前台程序。Windows 的进程树检测不提供 Unix 作业控制。

## 虚拟机与沙箱包装器

在 Linux 和 macOS 上,宿主可见的包装器可能会向 Herdr 隐藏真实的智能体进程。在包装器命令上设置 `HERDR_AGENT=<agent>`,告诉 Herdr 应使用哪个已有智能体的屏幕清单。例如,在 Linux 上运行 `HERDR_AGENT=claude fence -- claude`,或在 macOS 上运行 `HERDR_AGENT=claude nono run --profile claude-code -- claude`。这个提示的作用范围只限于该前台进程;仅在 VM 或容器内部设置时 Herdr 无法看到它,而且除非所有继承的前台进程都应被视为该智能体,否则不要全局 export。

某些受限的 Linux 运行环境不会公开终端前台进程组。原生检测不可用时,以 `HERDR_PROCESS_DETECTION=child-groups` 启动 Herdr 服务器,即可选择启用直接子进程组推断。原生检测仍然优先,默认的 `native` 模式不会执行此推断。这个选择加入模式属于尽力而为,较新的后台任务可能会被误判为前台任务。该变量由服务器读取且需要重启;请在远程服务器环境中设置,而不是在连接客户端上设置。

## blocked 状态

对屏幕清单类智能体,blocked 检测刻意从严。只有当实时底部缓冲区快照匹配已知可见的审批、提问或权限 UI 时,Herdr 才标记 `blocked`。对已知智能体,如果没有任何清单规则匹配,Herdr 会回退到 `idle`,并在 explain 输出中把该回退标记为 `default_known_agent_idle_fallback`。

不常见的新智能体提示可能显示为 `idle` 而不是 `blocked`,直到 Herdr 学会那种屏幕形态。检测本身不会发送输入,但信任错误 idle 状态的自动化可能向审批对话框输入内容。遇到意外提示时,请先检查再继续发送输入;idle 状态不代表获准批准操作。

用 Ctrl+Z 挂起智能体后,只要同一个进程仍在 shell 或其他非智能体命令后面存活,其名称、会话引用和钩子权限就会保留。用 `fg` 返回后继续使用该身份。另一个被识别的智能体接管前台的情况不在此范围内。保留身份不代表挂起的智能体能接收输入;发送提示前请检查窗格。

智能体会话开始前等你做决定的启动提示也算阻塞界面,例如 Codex 的「Hooks need review」选择框和 Kimi Code CLI 的「Trust this folder?」提示。提示打开期间窗格为 `blocked`,`herdr agent start` 会报告智能体尚未就绪,而不是直接返回成功。只有这类提示是屏幕上最后的内容时 Herdr 才按提示处理,所以智能体在输出里原样引用提示文字时不会被标成 `blocked`。

## 待处理事项与失败

除了状态,智能体还可以带一件需要你处理的事。`herdr agent get`、`herdr agent list` 和 socket API 以 `attention` 返回它,字段见[智能体待处理事项与洞察](/zh-cn/docs/socket-api/#智能体待处理事项与洞察)。它从不改变智能体状态、等待和汇总。

智能体处于 `blocked` 时,这件事就是它正在问的问题。问题和回答选项来自集成的 `herdr pane report-agent-attention --kind needs_input` 上报,或完整生命周期集成随 `blocked` 上报带来的消息。智能体进入 `blocked` 时如果 Herdr 已经知道这个问题,它也会成为需要处理通知的正文。智能体一离开 `blocked`,它就被丢弃。

一个回合失败时,Herdr 会保留这次失败,直到你看过为止。失败来自集成的 `--kind failed` 上报、智能体会话里的错误(见[会话洞察](#会话洞察),且错误记录自己的时刻不早于当前回合开始),或智能体进程在 `working` 时退出。更早回合留下的错误、或没有时刻的错误,只在洞察里显示,从不算作失败。Herdr 用「失败」通知和需要处理时的提示音告诉你;智能体工作期间记下的失败在这一回合结束时才通知。智能体重新开始工作、通知之后你看到该窗格所在的标签页、智能体被释放或被另一个智能体替换,或收到 `--kind clear` 上报时,失败清除。

一个回合只发一次结局通知。「失败」通知之后,这一回合不再发别的通知或提示音:第二次失败(例如集成报过之后又从会话里读到同一个错误)不再记录,智能体变为 `idle` 或 `blocked` 也不再发「已完成」或「需要处理」通知。对于会话洞察能读取错误的智能体(Claude Code、Codex、Kimi Code CLI 和 OpenCode),回到 `idle` 时请求后台刷新,并暂存完成通知,直到该次读取结束或最多等待 1.5 秒。读到属于这一回合的新错误时只发「失败」,否则只发「已完成」。来源暂不可读时立即放行;没有此能力或没有会话来源的智能体不等待。结局确定之后才读到的错误仍会出现在待处理事项里,但不再发第二次通知或提示音。下一次 `working` 复位结局。这段短等待与通知投递延迟([`[ui.toast]`](/zh-cn/docs/configuration/#通知) 的 `delay_seconds`)独立,不会阻塞终端输出或渲染。

单独按下 `ctrl+c` 或 `esc` 视为打断智能体。按键后 1.5 秒内智能体变为 `idle` 时,Herdr 不发完成通知、不响提示音,这段时间内退出的智能体进程也不算失败。这只针对在 Herdr 客户端和 `herdr agent attach` 中按下的键;通过 CLI 或 socket API 发送的键不算。

Herdr 还会为每个回合计时。`insight.working_since_ms` 是当前回合开始的时刻,只在智能体工作时存在;`insight.state_changed_at_ms` 是状态最近一次变化的时刻;`insight.last_turn_ms` 是上一个工作回合用了多久。前两个是 Unix 毫秒,最后一个是以毫秒计的时长。

## 会话洞察

Herdr 还会读取每个智能体会话的简短摘要,`herdr agent get`、`herdr agent list` 和 socket API 以 `insight` 返回它(字段见[智能体待处理事项与洞察](/zh-cn/docs/socket-api/#智能体待处理事项与洞察))。它和活动树在同一次读取里、按同样的节奏从智能体自己的会话数据读出:智能体工作时每 5 秒一次、收到钩子信号后,以及工作结束时再读一次。读取有上限,会话文件不变时 Herdr 不会重读。

| 智能体 | 读取来源 | 提供的内容 |
| --- | --- | --- |
| Claude Code | 会话转录的最后 1 MiB | 标题(你设置的标题,否则用 AI 生成的标题)、模型、最后提示、最后回复、当前工具、未作答的 `AskUserQuestion` 及其选项、API 错误 |
| Codex | 线程 rollout 的最后 1 MiB,线程名取自 `session_index.jsonl` | 线程名、模型、最后提示、最后回复、当前工具、未作答的 `request_user_input` 及其选项、失败回合的错误 |
| Kimi Code CLI | `state.json` 与主智能体 `wire.jsonl` 的最后 1 MiB | 标题、模型、最后提示、最后回复、当前工具、待答问题及其选项、失败回合的错误 |
| OpenCode | 一条只读的 `opencode db` 查询,数据库变化时才重查 | 标题、模型、最后提示、最后回复、当前工具、运行中的 `question` 工具及其选项、最后一条回复的错误(你按下的中止不算错误) |
| Pi | Herdr 的 Pi 扩展上报的活动快照 | 只有当前的扩展工具;扩展不上报消息和模型 |

ZCode 运行在 Herdr 窗格之外,它的外部条目没有洞察。OpenCode 只在内存里保存待批准的权限请求,所以它们不会作为问题出现。

文本都是去掉 Markdown 的单行;最后提示、最后回复、问题和错误最多保留 220 个字符。斜杠命令的输出、系统提醒、任务通知以及 `AGENTS.md` 之类注入的上下文都不算提示。当前工具是最近一次还没有结果的工具调用,显示为动词加对象,例如 `Shell cargo test` 或 `Edit src/app.rs`,路径相对智能体的工作目录;回合结束或被中断时清空。`error` 只反映最近一个回合:新的提示或正常的回复会把它清掉。`updated_at_ms` 是 Herdr 用到的最新会话记录的时刻,不是读取的时刻,所以会话没有变化时洞察完全相同,客户端也不会收到新的快照。

## 活动状态

活动树的每个节点都有一个状态:`pending`、`running`、`blocked`、`done`、`failed` 或 `unknown`。Herdr 用同一张表把各家来源自己的状态值映射过来:

- 等待中或排队的工作是 `pending`;运行中或进行中的工作是 `running`;停下来等你的运行中工作(例如 Kimi Code CLI 的提问任务)是 `blocked`。
- 已完成的工作是 `done`。被取消的计划条目(例如智能体撤下的待办)也是 `done`,因为是计划变了,而不是失败了。
- 出错、失败、被杀、被停、中止、打断、超时,以及被取消的运行中工作(子智能体、任务、后台进程、回合)都是 `failed`,因为工作没有完成。节点摘要通常会写明原因,例如 `killed` 或 `timed out`。
- 丢失和认不出的值是 `unknown`。

## 检测清单

内置清单打包在 Herdr 内部。Herdr 还会向 herdr.dev 检查远程清单更新,并自动应用有效的按智能体规则更新,不需要重启 Herdr。后台检查每 6 小时最多执行一次,且在首帧渲染完成后才开始;`herdr server update-agent-manifests` 手动拉取不受节流限制,始终立即执行。远程清单存放在 Herdr 的状态目录中。设置 `[update] manifest_check = false` 可以禁用后台远程清单检查。

本地覆盖可以从平台配置目录替换远程或内置清单:

```text
~/.config/herdr/agent-detection/<agent>.toml
```

本地覆盖始终优先。没有本地覆盖时,Herdr 在缓存的远程清单和运行中二进制文件内置的清单之间,选择更新且兼容的那个。在调试构建上,同一个配置助手可能使用 `herdr-dev` 之类的开发目录。无效的覆盖文件会被忽略并给出警告,Herdr 会对该智能体回退到缓存的远程或内置清单。

识别这两种提示的规则与内置、远程清单分开存放。Herdr 把它们叠加到当前生效的内置或远程清单上,远程清单更新不会把它们冲掉;生效清单里已有同 id 的规则时以该规则为准。本地覆盖替换整份清单,只运行覆盖文件里的规则。

远程清单只为 Herdr 已经知道如何识别的智能体修补检测规则。添加全新的智能体仍然需要更新 Herdr 二进制文件,以获得进程检测、标签和集成行为。

运行中的服务器在启动时把生效的清单加载进内存。自动的远程清单更新会在写入新规则后重新加载该内存缓存。运行 `herdr server update-agent-manifests` 可以立即拉取远程清单更新并重载运行中的服务器。手动编辑本地覆盖后,重启 Herdr 或运行 `herdr server reload-agent-manifests` 把文件应用到运行中的服务器。

当某个窗格显示了错误状态时,用 `herdr agent explain`:

```bash
herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json
```

实时 explain 由运行中的服务器评估,因此反映的是生效的清单缓存。explain 输出包括: 智能体、最终状态、屏幕检测是否被完整生命周期权威跳过、清单来源和版本、缓存的远程版本、本地覆盖的遮蔽情况、远程更新状态、匹配的规则、可见证据标志、已评估规则的匹配器和区域证据、转写查看器的跳过更新原因,以及没有规则匹配时的 idle 回退原因。

Herdr 可以在 tmux 作为外层终端环境时运行。智能体检测不会检查在 Herdr 窗格内启动的 tmux 会话。如果某个 shell 框架在 Herdr 内自动进入 tmux,Herdr 看到的窗格进程就是 `tmux`,而不是它背后的智能体。

如果你的 shell 在 `TMUX` 未设置时自动连接 tmux,请更新 shell 启动条件以排除 Herdr 窗格。从 Herdr 窗格内重新连接外层 tmux 会话可能导致终端尺寸递归缩小、画面闪烁。在现有条件中加入 `HERDR_ENV` 检查,并确保它在运行 tmux 之前生效:

```zsh
if [[ -z ${TMUX:-} && ${HERDR_ENV:-} != 1 ]]; then
  tmux new-session -A -s my-session
fi
```

## 状态汇总

侧边栏会把状态向上汇总。

一个 blocked 的智能体会让它的窗格、标签页和工作区看起来是 blocked。一个 working 的智能体会让工作区看起来处于活跃状态。一个 done 的智能体在你查看之前会一直保持可见。

这就是 Herdr 的主要工作流: 启动多个智能体,让它们并行工作,用侧边栏看哪个项目需要决策、哪个还在运行、哪个已经可以审阅。

## 自定义智能体标签

你可以重命名智能体目标的显示名:

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

目标使用唯一的实时智能体名称,或当前承载该智能体的窗格 ID。终端 ID 和单独的智能体 kind 标签不能作为目标。

## 自定义状态标签

集成只把生命周期状态作为语义状态上报。展示自定义应通过窗格元数据令牌单独添加。

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

`state` 控制等待、通知和汇总。`summary` 令牌只影响展示,可在智能体侧边栏行中写成 `$summary`。

智能体侧边栏行也可以选择使用 `terminal_title` 或 `terminal_title_stripped`;两者都不在默认行中。前者显示经过安全规范化的最新 OSC 0/2 终端标题,后者会移除开头一个已识别的活动或旋转指示符字形及其后的空白。这些值由 Herdr 服务器所有,冷重启后不会保留,并且独立于元数据标题和语义智能体状态。因此,如果移除后的文本不变,旋转动画可以改变原始标题而不触发窗格更新。

## 直接附加到智能体

把当前终端附加到某一个智能体终端,而不是完整的 Herdr UI:

```bash
herdr agent attach reviewer
```

用 `ctrl+b q` 分离。用 `ctrl+b ctrl+b` 发送字面的 `ctrl+b`。

用鼠标滚轮或普通的 page up/page down 滚动。正常输入会跳回底部。

如果另一个直接附加客户端已经拥有输入,用 `--takeover`:

```bash
herdr agent attach reviewer --takeover
```

想对非智能体终端获得相同的直接附加行为时,用 `herdr terminal attach <terminal_id>`。
