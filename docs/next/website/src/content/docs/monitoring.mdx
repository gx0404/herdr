Open **Monitor** from the top bar, the main menu, or command search. A single panel hosts three pages — System, Accounts and Monitor preferences — switched with the in-panel tabs or `1`/`2`/`3`; `r` refreshes, `Space` pauses history, and `Esc` closes, and the panel footer lists them as clickable hints — refresh on the System and Accounts pages, pause on the System page, close everywhere; the Monitor preferences page holds only local preferences, so its footer offers no refresh. Hardware metrics belong to the connected host; hovering a remote agent queries account usage on that agent's host.

## Menus, pages, and stable selection

`prefix+Space` opens the categorized main menu; `prefix+/` opens command search (the default prefix is `Ctrl+B`). Categories cover workspaces and agents, tabs and panes, machines and SSH, monitoring and usage, tools and automation, appearance and settings, and help and notifications. Recent commands are limited to five. Search matches action titles in either interface language, shortcuts, category names, and machine addresses. The wheel scrolls independently; keyboard navigation reveals the selected item.

Drag a page's top border to move it, or its side and bottom borders to resize it. Client preferences retain geometry and constrain it to smaller terminals. Layout locking also disables page dragging. Closing the menu restores the previous page. Settings apply on Enter or the **apply** button; theme selection previews and Escape cancels the preview.

Selecting terminal text freezes a text snapshot of that pane while processes and other panes keep updating. Release copies and resumes live output. With `copy_on_select` disabled, Ctrl+C copies the retained selection. Scrolling reads captured history without scrolling the live terminal. If output changed before capture and the mouse was already released, confirm the captured selection with Ctrl+C instead of automatically copying unseen content.

Each snapshot is bounded to 65,536 cells, 2048 rows, and 8 MiB; scrolling stops at the captured boundary. Server limits are 64 MiB, 32 snapshots, and one per client. Resize, target changes, cancellation, and disconnect release the snapshot. Unacknowledged captures expire after 60 seconds. Older servers retain the legacy selection path.

Use `Ctrl+Shift+Space` as the WezTerm leader and keep `Ctrl+B` for Herdr. Ordinary dragging selects within Herdr; Shift+drag uses WezTerm's selection.

## Docking

Drag a panel's `⠿` title handle to another panel's edge. The drop preview shows the destination. Drag dividers to resize, tabs to reorder or create another terminal group, and pane handles to swap panes or move them between tabs without restarting their processes. Borderless panes show their handles only in **Arrange layout** mode, keeping normal terminal text unobstructed. Right-click tab menus remain available.

The primary terminal page belongs to the focused workspace: clicking a workspace in the sidebar swaps both the tab strip and the terminal content to that workspace's tabs, numbered from 1 per workspace. Tabs dragged into their own panel stay visible regardless of workspace focus.

`□` maximizes a panel; while one is maximized the button shows `◫` and restores the layout. **Arrange layout** in the top bar enters arrange mode and stays highlighted while it is on; the footer then names the mode and lists its keys: `Tab` selects a panel (`Shift+Tab` goes back), arrows resize, `Shift+arrows` move, `Enter` maximizes, and `Esc` finishes (the footer's **Esc done** hint is clickable too). While a panel is maximized the whole layout still responds: `Tab` moves the maximized panel along with the focus, and arrows or `Shift+arrows` leave maximize first so the resize or move is visible. **Lock layout** is an on/off toggle that carries a check mark while the layout is locked and prevents accidental rearrangement; **Reset**, shown in arrange mode, restores the default layout; while the layout is locked it is dimmed and clicking it does nothing. Layouts persist per client and endpoint. Small terminals project the focused panel without discarding the saved layout. Older servers retain the previous single-view UI.

The Monitor panel carries a ` × ` button in its header next to `□`. Inside the docked panel the page draws no frame of its own — the panel header and divider already frame it — so its tabs sit on the first line below the panel header and its cards one column in from the panel edge. When the panel is focused, `Esc` closes the panel hosting the page; when a terminal is focused, `Esc` goes to the terminal, so use the header button or **Close monitor panel** in command search (listed only while the Monitor panel is docked). With the layout locked, closing is refused and the panel footer says so. The monitor tab you last selected — System, Accounts or Monitor preferences — is kept in client preferences and restored when the panel regains focus or the client restarts; opening **Monitor** from the top bar, the main menu, or command search starts on the System page. A docked Monitor panel no longer hides the focused terminal's cursor: the cursor disappears only where a panel, a usage popover or a dialog actually covers it.

When the terminal is too narrow for the whole top bar, buttons are hidden whole instead of being cut off: **Monitor** goes first, then **Lock layout**, then **Arrange layout** (all three remain in the main menu and command search), while **Reset**, which exists only in the top bar, is kept after them.

## Host resources

Choose total/per-core CPU, RAM/swap, GPUs, disks, network interfaces, temperatures and processes. Sampling supports 500, 1000, 2000 and 5000 ms. Slow collectors run independently. Initial differential samples, unavailable drivers and permission failures display a status or `—`, rather than zero.

NVIDIA uses NVML. Other Linux GPUs use driver-exposed DRM/sysfs fields; Windows uses DXGI and native GPU performance counters. Temperature, power and utilization availability depends on the driver. Containers and WSL report resources visible in that environment.

The System page opens with a host summary line — host name, operating system, uptime, sample age and sampling interval — and lays the resource cards out below it in one column, or two columns once the panel is at least 96 columns wide. The CPU card shows the total as a gauge whose number stays visible at any width, the model (or the selected core once you click one), and a history sparkline; the per-core card draws one mini bar per logical core, spread across the whole card width, and clicking a core selects its history. Memory shows used and cache as segments of one gauge plus a swap gauge; each GPU lists temperature, utilization and VRAM. Disks are a table of real data volumes: pseudo filesystems without capacity are skipped and a device mounted in several places is listed once. Network draws a stacked receive/transmit sparkline per active interface and folds idle interfaces into one line. Temperatures are summarised per chip: the number and bar show the hottest sensor, followed by the chip's average, which a narrow panel drops first; when every chip fits with at least two rows to spare, the card plots the hottest sensor's history below them. Within one card the bar rows share a label column and a number column, so their bars start and end at the same columns. Processes are a table whose headers sort on click; the row above it holds the name filter and the visible range, and the PID column is as wide as the longest PID in the sample, so seven-digit PIDs are never cut off. Scroll inside a card to inspect additional devices, cores or processes; over a card whose content already fits, such as CPU or memory, the wheel scrolls the page instead. Elsewhere on the page the wheel, and `↑`/`↓` while no card is selected, scroll one row of cards at a time, and `PageUp`/`PageDown` a screen at a time; scrolling stops once the last card is fully in view, so turning back moves the page on the first notch. Until then the next row of cards shows its top at the bottom edge of the page, cut off by the edge rather than squeezed into a shorter card. The Monitor preferences page scrolls three lines per notch and stops at its last line the same way. History is client-local, covers 1–60 minutes and has a 16 MiB budget. Pause stops history recording while live sampling and alerts continue.

Card order is changed in **Edit layout** mode, entered from the button at the right end of the summary line: every card gets ↑/↓ buttons on its top edge, once a card is selected the others dim, and the `↑`/`↓` keys move the selected card. **Done** or `Esc` leaves the mode; `Esc` closes the panel only on the next press. Card height, hidden devices and the chart glyphs are set on the Monitor preferences page.

Process details pin the process instance. Termination requires confirmation; force is a separate choice. Expired confirmations, reused PIDs and protected processes are rejected. Windows termination requires the force option and appropriate permission.

Alerts default to off and operate only while a TUI is connected. Configure threshold, duration and cooldown; alerts never kill processes. The Monitor preferences rows and the alert notification name each rule by its metric — CPU, Memory, GPU or Disk — rather than by its config id.

The **Monitor preferences** page groups its controls into cards. Steppers set the sampling interval (500 / 1000 / 2000 / 5000 ms), card height (7 / 10 / 16 / 24 rows), history range (1 / 5 / 15 / 30 / 60 min), the hover delay and each alert rule's threshold (50–100 % in steps of 5), duration and cooldown; toggles switch alerts, provider account usage, the visible cards, the listed providers and the sampled devices; segmented controls pick the usage format, the usage placement and the chart glyphs. A stepper moves to the neighbouring step of its fixed ladder and wraps at both ends, so a config value that sits between two steps moves to the next step first instead of skipping one. **Chart glyphs** selects the alphabet of the System page's sparklines and bars — Braille (default), Blocks, or ASCII for terminals without those glyphs — and is stored as the client preference `monitor_chart_glyphs`.

```toml
[monitor]
interval_ms = 1000
history_minutes = 15
visible = ["cpu", "cores", "memory", "gpu", "network", "processes"]
card_height = 10
hidden_devices = []
alerts_enabled = true # default: false

[[monitor.alerts]]
metric = "cpu" # cpu / memory / gpu / disk
threshold = 90
duration_seconds = 30
cooldown_seconds = 60
```

`visible` takes any of `cpu`, `cores`, `memory`, `gpu`, `disks`, `network`, `sensors`, and `processes` (all eight by default), and an alert's `metric` is `cpu`, `memory`, `gpu`, or `disk`. Listing `[[monitor.alerts]]` replaces the built-in rules (CPU, memory, and disk at 90 %, GPU at 95 %, each for 30 s with a 60 s cooldown). Changing the sampling interval, card height, history range, visible cards, sampled devices, or alert settings on the Monitor preferences page, or moving cards in **Edit layout**, saves the whole monitor configuration as the client preference `monitor`, which from then on takes precedence over `[monitor]` in the config file; **Restore config file values** resets only the account usage settings.

## Account binding

Hover an agent row or CLI title to inspect usage. `format` picks dashboard gauges or a table. `position` decides where that per-pane popover lives: `hover` and `both` keep it on agent rows and CLI titles; `page` turns the pointer popover off, leaving the accounts page and the right-click **Usage** card described below as the per-pane views (the Monitor preferences page shows a hint while it is selected). The accounts page is available in every mode. Choices made in Monitor → Monitor preferences are saved as client preferences that override `enabled`, `format`, `position`, `hover_delay_ms` and the disabled providers on that machine until "Restore config file values" is used there. Select and bind the account to the pane. A shared vendor name does not identify an account by itself: when an official callback arrives from an unbound pane and that vendor has exactly one configured account, the server binds the pane to it, persists the binding and marks the snapshot as auto-bound; with several accounts for the vendor the callback is rejected with the candidate list and the pane must be bound explicitly. Auto-binding requires `account_usage.enabled` and, for an official callback, a callback that carries quota fields.

The per-pane usage popover on agent rows and CLI titles appears after `hover_delay_ms` (400 ms by default) and closes 250 ms after the pointer leaves the row and the popover. In the classic layout, while a monitor page covers the pane area, the pointer popover is not shown and sends no usage query until the page closes; a card pinned from the right-click **Usage** entry still shows over the page. It keeps its own scope: showing it or binding from it never changes the accounts page selection, but its **Switch account** action also switches the selection on the accounts page, and its **Open page** button opens the accounts page. The cross-provider overview lives on the accounts page: its first chip, **All providers**, shows every listed provider at once. When the overview has no account to show it says why instead of asking you to pick a provider: the host has no provider CLI or configured account, every listed provider is turned off in Monitor preferences, the query is still running, or no listed provider has an account to query. A selected provider without accounts, including the usage card on an agent row, is explained the same way: it is turned off in Monitor preferences, this host has neither its CLI nor an account configured for it (the server only creates accounts for installed providers), this host does not report usage for it, or the query was answered with no account to query. "Querying" appears only until the first answer arrives, in the overview as well.

The same card can be opened on purpose: right-click an agent row and choose **Usage**. It appears at once and stays pinned — its title reads `<agent> · Usage`, with a **pinned** marker at the right end of its top border — so moving the pointer away or over other agent rows does not close or replace it; press Esc or click anywhere outside the card to close it. The entry works under every `position`, including `page`, and in the classic layout a pinned card is also drawn over an open monitor page. When account usage is turned off in Monitor preferences, the card says so instead of loading. Cards opened from an agent row, hovered or pinned, sit beside the Agents panel — to its right, or to its left when the panel is docked against the right edge — starting on the line just below the row, or ending just above it when there is no room below, so they never cover neighbouring agent rows; when neither side of the panel has 40 free columns they open directly below or above the row instead. Cards opened from a CLI title open directly below the title row, left-aligned with it (shifted left when the right edge is too close), and flip above the title when there is no room below. When neither side is tall enough a card takes the larger side and shrinks, and a card that would be shorter than five rows is not shown; a card never covers its own row or title.

Client preferences are read field by field: an unreadable value (for example an unknown `usage_format` or `monitor_chart_glyphs`) drops only that field with one diagnostic and keeps the rest. The `usage_*` keys are written back only once they have been set explicitly.

The accounts page lists only providers whose official CLI is installed on the connected host — resolved with the same multi-alias PATH and install-layout detection as the integrations settings page (for example codex standalone/nvm/volta/bun), so both surfaces agree. ZCode has no CLI to look for: it is listed when its local database `~/.zcode/cli/db/db.sqlite` exists on the connected host. Providers with an explicitly configured account stay listed. `account.usage.providers` reports an `installed` flag per provider; older servers omit the field and keep listing the full registry. Automatic refresh runs on the server while a client shows the data: API accounts every `api_refresh_seconds` (at least 60 s), CLI probes every `cli_refresh_seconds` (at least 300 s; `account.usage.providers` advertises the effective value as `minimum_interval_seconds`; ZCode's local database read runs on the same schedule), with bounded backoff after failures. Vendors fed by an official callback (Claude Code) or by Herdr's own integration extension (Pi) advertise no polling interval and are refreshed by those pushes. When the accounts page opens without a provider selected it picks the agent running in the focused pane, otherwise the first listed provider. Switching provider or account keeps the previous snapshot dimmed until fresh data arrives; "Switch account" is disabled when the current scope has fewer than two configured accounts, and providers turned off in settings leave the provider chips, the switch candidates and the overview at once. When a codex CLI is found through an install layout, the probe runs it with that layout's bin directory first on `PATH` so npm-shim CLIs resolve their interpreter.

On a wide panel (96 columns and up) the detail column also plots how the selected account's tightest quota window moved over time: the client keeps the last 120 samples it saw (polling responses and subscription pushes alike) and draws the most recent ones that fit the column as a sparkline under "Usage history". With fewer than 8 samples the sparkline is a single-row strip, and even with more it stays a small chart of at most 6 rows instead of stretching down the whole column.

An explicit refresh (`account.usage.refresh`, the account page's refresh action, switching provider or account) is debounced to 10 s per account and still honors vendor backoff (HTTP 429); a debounced response carries `next_allowed_at_ms`. Terminal results (not signed in, unsupported, permission denied) are retried automatically on a slow schedule — 10 min, doubling up to 1 h, at most 6 times — and the hold is lifted as soon as the CLI binary or its credential files change, so signing in heals the account without a restart; an explicit refresh always retries a terminal state. Official callbacks without quota fields do not overwrite the cached sample. After 15 min without a callback the snapshot is shown as cached data; probes may fall back, but only a successful probe or the next callback replaces it. Push-fed vendors (Claude Code's official callback while `interactive_probe` is off, Pi's extension push) report `callback_only` in the refresh state: an explicit refresh cannot produce a new sample for them, though it may still refresh a login or binding placeholder.

While the accounts page is visible, the client subscribes with `account.usage.subscribe` on servers that advertise it and applies pushed `account.usage.updated` / `account.usage.refreshing` events as they arrive, keeping only a 30 s fallback poll; the subscription is dropped when the page is hidden, re-established after a reconnect, and older servers fall back to polling (2 s, or 500 ms while a probe is in flight). An account being probed shows "Refreshing…" in place of its status — on its card's badge (on the status line for local and session stats cards) or in the table's status column — so it never reads "Current" and "Refreshing…" at once, while the card keeps saying how old its data is; the refresh button reads "Refresh in Ns" while the selected account (or, with no selection, every listed account) is still debounced, and a vendor backoff longer than a minute is noted on the account's row instead of locking the button. The accounts page also carries a binding row: a pane picker that only offers panes running the selected provider's agent, "Bind focused pane", and one-click candidates from `pending_binding` after the server rejected a callback from an unbound pane. Every binding entry refuses a pane running another provider's agent, and enabling the official callback binds the pane on the host that answered — never on a host that became active meanwhile.

Claude Code is callback-first. Quota comes from the official statusline callback; probes only check the login state with the non-interactive `claude auth status --json`, which reads the real login store read-only. A signed-in account without the callback says that it is waiting for the official statusline callback, which you turn on with the **official callback** toggle on the accounts page, and that precheck backs off on the same slow schedule as terminal states until the first callback arrives. That message, like the interactive probe's folder-trust and sign-in hints and the other fixed notes on the cards and in the table's status column (not queried yet, the stale-callback note, the pi waiting note, and so on), is shown in the language of the client viewing it, whatever language the server runs in; the table also names known metrics in that language. Provider error text is shown as reported. The interactive `/usage` probe is opt-in (`interactive_probe = true`) and runs on explicit refresh only, inside a stable probe directory under the herdr state directory: Claude Code asks you to trust that directory once in your own CLI — the refresh state reports `trust_required` and the message names the directory — and herdr never answers that dialog for you. Because the interactive probe reuses the real login state, concurrent launches can rotate credentials; leave it off unless you need `/usage` without the callback.

Besides the account windows in `rate_limits` (`five_hour`, `seven_day`, and `spend_limit` behind a Claude apps gateway), the callback also carries the reporting session's estimated cost, wall-clock and API time (`cost.*`) and its context window (`context_window.*`). Those are listed as session statistics, never as account quota, and they describe whichever session reported last when several share one account. Three details follow the official statusline contract: Claude Code drops a window from the JSON once its `resets_at` passes (and omits `rate_limits` before a session's first API response), so a missing window keeps its last value instead of becoming zero, and is labelled as past its reset time once that time has gone by (a kept window is dropped a week after its reset time, or a week after it last appeared if it came without a `resets_at`); `context_window.current_usage` and `used_percentage` are `null` before the first API call and right after `/compact`, which is shown as "no data yet" rather than 0; and `spend_limit` can exceed 100 %, which is kept as reported. A callback that has no `rate_limits` at all (an older CLI, or an API-key login) and no earlier window to keep does not take over the account.

The dashboard format draws one card per account, laid out by provider. The card's top border carries the account label and its status; the first line inside shows sample age, plan and identity (and the status, when the badge is a statistics notice). Claude Code shows the 5-hour, weekly and spend-limit windows as gauges, followed by the session's context usage and cost: the spend limit keeps its reported value above 100 % and ends its bar with an overflow marker `▸`, and a window whose reset time has passed keeps its last value in gray, with a dimmed bar and a "past reset" note. Codex shows the primary and secondary window of every rate-limit bucket, named after the window length (for example "5h window"), plus the bucket's credits; several buckets get one section each. Kimi Code shows the 5-hour, 7-day and monthly windows, the balances in their currency and the extra-usage wallet. OpenCode and ZCode cards carry a "Local stats, not account quota" badge and show their figures (sessions, cost, tokens, tool uses) as plain numbers without gauges. Pi's card carries a "Session stats" badge: a context gauge, the session cost and model, and the token breakdown; until the first push arrives the card explains what it is waiting for. A ZCode card appears only when the connected host reports a ZCode account. Metrics a card does not recognise are still listed as generic rows, and an unknown provider gets a generic card. Gauges are colored by threshold and carry a tick for how much of the window has passed (the 5-hour, weekly and 7-day windows by their fixed length, other windows only when the provider reports one), turning yellow or red early when usage runs ahead of time; on a narrow panel the bar shrinks and disappears before any number does. Rows of figures treat each label and number as a whole: a pair that no longer fits is left out instead of being cut in half, and the pairs that remain close up. With **All providers** selected in the dashboard format and accounts from more than one provider, the page shows one compact card per provider instead — the tightest quota window (or the key figure for local and session statistics) and a status line — in two columns from 96 columns up; clicking a compact card, or pressing Enter on it, opens that provider. In the agent-row popover a card never grows taller than the popover: rows that do not fit are counted as "+N" on its bottom border, and **Open page** shows the whole card. The popover itself is only as tall as its content needs, up to 17 rows, so a short card leaves no empty band below it.

Both formats support wheel scrolling; the account page also supports the arrow keys for quota windows below the viewport. The usage popover can appear over a focused monitor panel and captures its own input without activating background cards or process rows.

Subscription windows, key budgets, organization billing and local session statistics keep their own scopes and units. Results show reset times, source and sample age. Temporary errors retain the last successful sample with a cached status and bounded retry intervals.

Configure accounts on the server running the agent. `credential_env` names an environment variable; do not place the credential itself in TOML. Herdr does not copy CLI OAuth credentials to clients. CLI profiles use the vendor's documented directory selector. Kimi Code uses `KIMI_CODE_HOME`; its login state lives in `credentials/kimi-code.json` under that directory, and signing in there heals a "Sign in required" account without a restart.

```toml
[account_usage]
enabled = true
format = "dashboard" # dashboard / table
position = "hover" # hover / page / both; page turns the agent-row popover off
hover_delay_ms = 400
api_refresh_seconds = 60
cli_refresh_seconds = 300
probe_timeout_seconds = 20
interactive_probe = false # explicit refresh only; Claude needs a one-time folder trust
disabled_providers = []

[[account_usage.accounts]]
id = "work-codex"
label = "Work"
agent = "codex"
provider = "codex"
auth_mode = "cli"
profile_dir = "/path/to/profile"

[[account_usage.accounts]]
id = "team-api"
label = "Organization API"
agent = "claude"
provider = "anthropic"
auth_mode = "api"
credential_env = "ANTHROPIC_ADMIN_KEY"
```

For OpenAI API accounts, `organization` selects the organization (sent as the `OpenAI-Organization` header); `account_user` is deprecated: no provider uses it, so it is ignored, and an account that still sets it gets a config diagnostic asking you to remove it. API-key accounts cover OpenAI, Anthropic, Moonshot and OpenRouter. OpenRouter uses a management key with `billing_scope = "account"`; its default scope is the current API key. `base_url` only accepts registered official hosts; Kimi's local API is restricted to loopback.

## Official callbacks

The Claude Code account panel can enable/remove the official statusline callback. An existing renderer is retained at the end of a passthrough pipeline. Claude's quota fields require a supporting CLI version and normally appear after the first ordinary API response. Herdr never sends a model prompt to obtain usage.

Other integrations can send supported official JSON to stdin of `herdr api usage-report --agent <agent>`. The command uses the binding for `HERDR_PANE_ID`, or explicit `--account <id>`. An unbound pane is bound automatically only when the vendor has a single configured account; otherwise bind first. Raw reports and conversation contents are not persisted. `--passthrough` preserves input for an existing statusline renderer.

Pi has no statusline contract, and its RPC mode starts a separate headless process that cannot see the session running in your pane. Herdr's Pi extension (integration version `10`; run `herdr integration install pi` to update) reads the usage inside the running TUI session instead and pushes it over the Herdr socket: when the session starts, after each turn (at most once every 5 s), after a compaction and when the agent settles. The push carries the context gauge (`ctx.getContextUsage()`), the session's token and cost totals, and the current provider and model — the model the provider actually answered with when it differs from the requested one. Pi is a multi-provider CLI, so these are session statistics, not an account quota: the provider/model is there to relate the session to the subscription that pays for it, not to meter it twice. Right after a compaction Pi does not know the context size until the next response; Herdr shows that as "no data yet", not as 0. There is no callback switch for Pi; until the first push arrives the account explains what it is waiting for.

## Provider capabilities

Account usage covers six agents: Codex, Claude Code, Kimi Code, OpenCode, Pi and ZCode. Official sources were last checked on 2026-09-22 (Codex on 2026-09-16, the ZCode database schema on 2026-09-23). Subscription access and administrator billing access differ. Unsupported versions, absent APIs or missing permissions produce an explicit availability message, and an account configured for any other agent reports that no official source is registered. Session and local statistics never imply an account quota.

| Agent | Official source and scope |
| --- | --- |
| Codex | [App Server](https://learn.chatgpt.com/docs/app-server): account, rate-limit windows and credits. API billing uses the administrator reports. |
| Claude Code | [statusline JSON](https://code.claude.com/docs/en/statusline): `rate_limits` account windows, plus the session's `cost` and `context_window`; opt-in `/usage`. API organization usage and cost are separate. |
| Kimi Code | [local Server API](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/server-api.html) (experimental upstream): `quota.usages` windows — 5 h, 7 d, monthly, and the Code share of the monthly window — and the `quota.extraUsage` pay-as-you-go wallet as currency amounts (balance, total, this month's spend, and the monthly cap when one is enabled). Moonshot API balance is queried separately. |
| OpenCode | [`opencode db <query> --format json`](https://opencode.ai/docs/cli/): a read-only aggregate over the `session` table — sessions, sub-agent sessions, cost, and input / output / reasoning / cache tokens. Local statistics, not an account quota. |
| Pi | Herdr's Pi extension, built on the [extension API](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md): context usage, session tokens and cost, current provider/model. Session statistics, not an account quota. |
| ZCode | The local database `~/.zcode/cli/db/db.sqlite` of the [ZCode desktop app](https://github.com/zai-org/ZCode), read with the system `sqlite3 -readonly`: the last 24 hours of the `model_usage` table — tokens split into the main task and sub-agents plus their total, tool calls, and the number of sub-agent sessions. No credentials are needed or read. Local statistics only, not an account quota; the remote quota is not queried. |

OpenCode has no account-quota API, so both of its shapes are labelled as local session statistics in the metric scope and in the source line. The `db` query only reads counts and sums, never session titles or paths. CLI builds without the `db` subcommand or its `--format` flag, and queries that fail (for example against an older database schema), fall back to parsing the `opencode stats` table. OpenRouter key budgets are distinct from account totals. Kimi's Server API is marked experimental upstream, so missing or reshaped fields are skipped instead of failing the whole sample.

On the accounts page OpenCode and ZCode carry a "Local stats, not account quota" badge and Pi a "Session stats" badge, so none of them reads as an account quota. ZCode's local statistics come from the ZCode desktop app's database; its remote quota is not queried.

ZCode is a desktop app that never runs in a pane, and Herdr never launches it (its command opens a window). The server reads its database with the `sqlite3` command from its own `PATH`; without it the ZCode account says so instead of showing numbers. The query only counts and sums request rows by start time — it never reads prompts, messages or error texts. A request counts as a sub-agent's when its `query_source` is `subagent` or its `task_type` is `subagent_child`; every other request (the main turn, title generation, compaction) counts toward the main task. A locked, unreadable or reshaped database keeps the last sample as cached data and is retried with backoff. ZCode accounts refuse `herdr api usage-report` pushes and do not support `profile_dir`; add `"zcode"` to `disabled_providers` to stop the polling.

## API

Public JSON methods include `system.metrics.get/subscribe/unsubscribe`, `system.process.list/get/terminate`, `account.usage.providers/get/refresh/subscribe/unsubscribe/report/integration`, and `account.binding.set`. Slow subscribers retain the newest sample.

`account.usage.get` / `account.usage.refresh` responses and `account.usage.updated` events carry a `refresh` list (`UsageRefreshState`, aligned to `accounts` by `account_id`; older servers omit it) next to the snapshots: probe progress (`in_flight`, `queued`, `attempted_at_ms`), the explicit-refresh debounce (`requested_at_ms`, `next_allowed_at_ms`), vendor backoff (`retry_after_ms`), `binding_inferred`, `trust_required`, `callback_only`, `pending_binding` and `callback_enabled`. `account.usage.refreshing` pushes only that list as a probe starts. Field meanings and the event envelope are documented under [event subscriptions](/docs/socket-api/#event-subscriptions).

`client.views.set` and named view-frame/input extensions require a negotiated TUI connection. Generation 1 encoding stays unchanged. Pane dragging reuses `pane.move` and `pane.swap`. Use `herdr api schema --json` for the precise contracts.
