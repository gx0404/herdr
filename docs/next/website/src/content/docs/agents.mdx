Herdr is built for running more than one coding agent at a time. Each agent stays in a real terminal pane with its shell, logs, prompts, and running processes intact. Herdr tracks which panes contain agents, rolls their state up to tabs and workspaces, and lets you jump straight to the pane that needs attention instead of polling every terminal by hand.

The [Sessions sidebar](/docs/concepts/#session-sidebar) brings workspaces, tabs, agent sessions, ordinary terminals, and read-only External activity into one tree. `prefix+a` cycles through online pane sessions that need input, failed, or await review, in that order; it excludes offline caches and External entries.

To coordinate agents from scripts or from another agent, see [Agent automation](/docs/agent-automation/).

The agent overview (`prefix+g`) groups sessions as **Needs input → Failed → To review → Working → Idle**. Press `g` to switch to location navigation, which retains machines, workspaces, and ordinary terminals. Space opens a preview of the received insight, including questions, options, failure details, model and location; it does not claim to recover text already shortened by the server. Enter jumps to the real pane.

Use `r` / `u` / `R` to mark read, mark unread, or mark all read locally. A manual unread mark survives viewing that pane until you explicitly mark it read or the next turn/agent identity/server boot invalidates it. Up to 256 manual marks are saved per client across endpoints. Failure attention and lifecycle are not changed. Offline cached sessions are dimmed and cannot send actions.

For idle or review sessions, `e` opens a multiline reply draft only when that endpoint explicitly advertises `agent.prompt`. Enter inserts a newline; Ctrl+Enter or **Send** confirms submission with `wait = None`. Working, failed, and permission/question-blocked agents cannot be replied to here: use **Jump and answer** instead. Sending is single-flight; errors and timeouts keep the draft but never trigger an automatic retry. A changed target, boot, replacement identity, or closed overview fences late responses. A timeout does not prove the server failed to submit the prompt, so check the terminal before retrying.

## Supported agents

Agents get Herdr support in one of two ways: Herdr supports them, or they support Herdr themselves. Either way you see each agent's `idle`, `working`, and `blocked` state, get notified when it finishes or needs you, and can wait on it from scripts.

Other agents still run normally in Herdr panes. They just show up as plain terminals.

### Supported by Herdr

Herdr recognizes these agents and reads their state from what they draw on screen. To get the same session back after a Herdr server restart, install the agent's integration with `herdr integration install <name>`. See [Integrations](/docs/integrations/) for what each one installs.

| Agent | Integration | Notes |
| --- | --- | --- |
| Pi | lifecycle hooks when installed; otherwise screen manifest | state and session |
| Claude Code | screen manifest | session |
| Codex | screen manifest | session |
| OpenCode | lifecycle plugin when installed; otherwise screen manifest | state and session |
| Kimi Code CLI | lifecycle hooks when installed; otherwise screen manifest | state and session |

These five are the only agents this fork detects and ships integrations for; see [Retired integrations](/docs/integrations/#retired-integrations) for what happened to the others. Unsupported agents still run normally as terminal processes. They just may not get rich state unless you add an integration or report state over the socket API.

ZCode appears as a read-only external source only while a recent root session is running. When no session is running, its External group disappears. A session that has ended can still be read by its external ID while it remains unarchived and within the 72-hour recent window.

Activity-tree discovery uses bounded background queues. Sources that read session files (Claude Code, Codex, Kimi Code CLI, and Pi's reported snapshot) and sources that run a query program (OpenCode's `opencode db` and ZCode's `sqlite3`) each have their own queue and worker, so a slow query never delays discovery for the other panes. A pane still has at most one discovery in flight. A refresh rejected by a full queue remains eligible for retry under the normal throttle, including an idle pane's first discovery. ZCode transcript reads scan at most 8 MiB per call, skipping oversized lines in bounded pieces without interpreting their suffix as a new record. Pass returned cursors back unchanged to continue reading; a short unfinished transcript line waits for its terminating newline.

These agents report their own state to Herdr. There is nothing to install; run them in a Herdr pane.

## How status works

For agents Herdr supports, Herdr finds the agent's process in each pane and reads the live bottom of the pane, not the part you scrolled to. Rules in a detection manifest decide whether that screen means `idle`, `working`, or `blocked`. When an integration also reports state, Herdr uses those reports instead of reading the screen.

For agents that support Herdr, the agent's own reports decide the state.

When Herdr can verify that the same agent process is still alive in the pane, moving it out of the foreground does not discard its session identity, name, or lifecycle-hook authority. For example, suspending it with `ctrl+z` in a Unix shell and returning with `fg` keeps that identity. While it is held in the background, Herdr does not classify the foreground shell or another command's screen as the agent's state. A confirmed exit or a replacement agent process clears the old identity; this is not a separate `suspended` API status. Resume the intended job before sending it input: pane input still goes to the foreground program. Windows process-tree detection does not provide Unix job control.

## VMs and sandbox wrappers

On Linux and macOS, a host-visible wrapper can hide the real agent process from Herdr. Set `HERDR_AGENT=<agent>` on the wrapper command to tell Herdr which existing agent screen manifest to use. For example, run `HERDR_AGENT=claude fence -- claude` on Linux or `HERDR_AGENT=claude nono run --profile claude-code -- claude` on macOS. The hint applies only to that foreground process. Herdr cannot see it if you set it only inside a VM or container. Avoid exporting it globally unless every inherited foreground process should be treated as that agent.

Some restricted Linux runtimes do not expose a terminal foreground process group. Start the Herdr server with `HERDR_PROCESS_DETECTION=child-groups` to opt into direct child-process-group inference when native detection is unavailable. Native detection remains preferred, and the default `native` mode never performs this inference. The opt-in mode is best effort: a newer background job can be mistaken for the foreground job. The variable is read by the server and requires a restart; set it in the remote server environment rather than on an attaching client.

## Blocked state

Blocked detection is deliberately strict for screen-manifest agents. Herdr only marks `blocked` when the live bottom-buffer snapshot matches known visible approval, question, or permission UI. If no manifest rule matches for a known agent, Herdr falls back to `idle` and labels that fallback as `default_known_agent_idle_fallback` in explain output.

Unusual new agent prompts may initially show as `idle` instead of `blocked` until Herdr learns that screen shape. Detection itself does not send input, but automation that trusts a mistaken idle state can type into an approval dialog. Inspect unexpected prompts before sending more input; idle status is not authorization to approve an action.

Suspending an agent with Ctrl+Z preserves its name, session reference, and hook authority while the exact process remains alive behind the shell or another non-agent command. Returning with `fg` keeps that identity. This does not cover another recognized agent taking over the foreground. A retained identity does not mean the agent can receive input while suspended; inspect the pane before prompting it.

Startup prompts that wait for a decision before the agent session begins count as blocking UI too, for example the Codex "Hooks need review" chooser and the Kimi Code CLI "Trust this folder?" prompt. While such a prompt is open the pane is `blocked`, and `herdr agent start` reports that the agent is not ready instead of succeeding. Herdr counts such a prompt only while it is the last thing on the screen, so an agent that quotes the prompt's text in its output is not marked `blocked`.

## Attention and failures

Besides its state, an agent can carry one item that needs you. `herdr agent get`, `herdr agent list`, and the socket API return it as `attention`; see [Agent attention and insight](/docs/socket-api/#agent-attention-and-insight) for the fields. It never changes the agent state, waits, or rollups.

While an agent is `blocked`, the item is the question it is asking. The question and its answer options come from an integration's `herdr pane report-agent-attention --kind needs_input` report, or from the message a full-lifecycle integration sends with its `blocked` report. When Herdr already knows the question as the agent becomes `blocked`, the question is also the body of the needs-input notification. It is dropped as soon as the agent stops being `blocked`.

When a turn fails, Herdr keeps the failure until you have seen it. A failure comes from an integration's `--kind failed` report, from an error in the agent's session (see [Session insight](#session-insight)) whose own timestamp is not earlier than the start of the current turn, or from the agent process exiting while it was `working`. An error left over from an earlier turn, or one without a timestamp, is shown in the insight but never counts as a failure. Herdr announces it with a "failed" notification and the needs-input sound; a failure recorded while the agent is still working is announced when that turn ends. The failure clears when the agent starts working again, when you view the pane's tab after the notification, when the agent is released or replaced by another agent, or on a `--kind clear` report.

A turn has only one outcome notification. After the "failed" notification, the rest of that turn sends no other notification or sound: a second failure, such as the same error read from the session after the integration reported it, is not recorded, and the agent going `idle` or `blocked` sends no finished or needs-input notification. For agents whose session insight can report errors (Claude Code, Codex, Kimi Code CLI, and OpenCode), returning to `idle` requests a background refresh and holds the finished notification until that refresh completes or 1.5 seconds pass. A new error belonging to that turn produces only "failed"; otherwise Herdr sends only "finished". An unavailable read releases the notification immediately; agents without this capability or without a session source do not wait. An error read after the outcome is settled still appears in attention, but sends no second notification or sound. The next `working` state resets the outcome. This short wait is separate from the toast delivery delay (`delay_seconds` in [`[ui.toast]`](/docs/configuration/#notifications)) and never blocks terminal output or rendering.

Pressing `ctrl+c` or `esc` on its own counts as interrupting the agent. If the agent goes `idle` within 1.5 seconds of that key, Herdr sends no finished notification or sound, and an agent process that exits in that window is not counted as a failure. This covers keys typed in the Herdr client and in `herdr agent attach`; keys sent through the CLI or socket API do not count.

Herdr also times each turn. `insight.working_since_ms` is when the current turn started and is set only while the agent works, `insight.state_changed_at_ms` is when the state last changed, and `insight.last_turn_ms` is how long the last working turn took. The first two are Unix milliseconds; the last is a duration in milliseconds.

## Session insight

Herdr also reads a short summary of each agent's session, returned as `insight` by `herdr agent get`, `herdr agent list`, and the socket API (see [Agent attention and insight](/docs/socket-api/#agent-attention-and-insight) for the fields). It is read from the agent's own session data together with the activity tree, on the same schedule: every 5 seconds while the agent works, after a hook signal, and once more when work ends. Reads are bounded, and Herdr does not read again until the session's files change.

| Agent | Read from | Provides |
| --- | --- | --- |
| Claude Code | the last 1 MiB of the session transcript | title (your custom title, otherwise the AI title), model, last prompt, last reply, current tool, an open `AskUserQuestion` with its options, API errors |
| Codex | the last 1 MiB of the thread's rollout, plus `session_index.jsonl` for the thread name | thread name, model, last prompt, last reply, current tool, an open `request_user_input` with its options, a failed turn's error |
| Kimi Code CLI | `state.json` and the last 1 MiB of the main agent's `wire.jsonl` | title, model, last prompt, last reply, current tool, a pending question with its options, a failed turn's error |
| OpenCode | one read-only `opencode db` query, repeated only when the database changes | title, model, last prompt, last reply, current tool, a running `question` tool with its options, the error of the last reply (an abort you pressed is not an error) |
| Pi | the activity snapshot Herdr's Pi extension reports | the current extension tool only; the extension does not report messages or the model |

ZCode runs outside Herdr panes, so its external entries carry no insight. OpenCode keeps pending permission requests only in memory, so they never appear as a question.

Texts are single lines with Markdown removed; the last prompt, last reply, question, and error keep at most 220 characters. Slash-command output, system reminders, task notifications, and injected context such as `AGENTS.md` are not prompts. The current tool is the latest call that has no result yet, shown as a verb and its target, for example `Shell cargo test` or `Edit src/app.rs` with paths relative to the agent's working directory; it clears when the turn ends or is interrupted. `error` only covers the latest turn: a new prompt or a normal reply clears it. `updated_at_ms` is the time of the newest session record Herdr used, not the time it read the session, so an unchanged session yields an identical insight and clients are not sent a new snapshot.

## Activity status

Each activity-tree node has one of the statuses `pending`, `running`, `blocked`, `done`, `failed`, or `unknown`. Herdr maps every source's own status values onto them with one table:

- Waiting or queued work is `pending`; running or in-progress work is `running`; running work that waits for you (such as a Kimi Code CLI question task) is `blocked`.
- Completed work is `done`. A cancelled plan item, such as a todo the agent dropped, is also `done`, because the plan changed rather than failed.
- Errors, failures, kills, stops, aborts, interrupts, timeouts, and cancelled running work (sub-agents, tasks, background processes, turns) are `failed`, because the work did not finish. The node summary usually names the reason, for example `killed` or `timed out`.
- Lost and unrecognized values are `unknown`.

## Detection manifests

Bundled manifests live inside Herdr. Herdr also checks herdr.dev for remote manifest updates and applies valid per-agent rule updates automatically without requiring a Herdr restart. Background checks run at most once every 6 hours and only after the first frame renders; `herdr server update-agent-manifests` always fetches immediately and is not throttled. Remote manifests are stored in Herdr's state directory. Set `[update] manifest_check = false` to disable background remote manifest checks.

Local overrides can replace a remote or bundled manifest from the platform config directory:

```text
~/.config/herdr/agent-detection/<agent>.toml
```

Local overrides always win. Without a local override, Herdr uses the newer compatible manifest between the cached remote manifest and the bundled manifest in the running binary. On debug builds, the same config helper may use a development directory such as `herdr-dev`. Invalid override files are ignored with a warning and Herdr falls back to the cached remote or bundled manifest for that agent.

The rules for these two prompts are kept separate from the bundled and remote manifests. Herdr adds them on top of whichever of the two is active, so a remote manifest update does not drop them; if the active manifest already has a rule with the same id, that rule wins. A local override replaces the whole manifest, so only the rules in the override file run.

Remote manifests patch detection rules for agents Herdr already knows how to identify. Adding a completely new agent still requires a Herdr binary update for process detection, labels, and integration behavior.

The running server loads active manifests into memory on startup. Automatic remote manifest updates reload that in-memory cache after new rules are written. Run `herdr server update-agent-manifests` to fetch remote manifest updates immediately and reload the running server. After editing a local override manually, restart Herdr or run `herdr server reload-agent-manifests` to apply the file to the running server.

Use `herdr agent explain` when a pane shows the wrong state:

```bash
herdr agent explain <target>
herdr agent explain --file screen.txt --agent codex --json
```

Live explain is evaluated by the running server, so it reflects the active manifest cache. The explain output shows the agent, final state, whether screen detection was skipped by a full lifecycle authority, manifest source and version, cached remote version, local override shadowing, remote update status, matched rule, visible evidence flags, matcher and region evidence for evaluated rules, skipped-update reason for transcript viewers, and the idle fallback reason when no rule matched.

Herdr can run inside tmux as the outer terminal environment. Agent detection does not inspect tmux sessions launched inside a Herdr pane. If a shell framework auto-enters tmux inside Herdr, Herdr sees `tmux` as the pane process instead of the agent behind it.

If your shell automatically attaches to tmux whenever `TMUX` is unset, update its startup rule to exclude Herdr panes. Reattaching the outer tmux session from inside a Herdr pane can recursively shrink the terminal and make it flicker. Add the `HERDR_ENV` check to your existing condition before it runs tmux:

```zsh
if [[ -z ${TMUX:-} && ${HERDR_ENV:-} != 1 ]]; then
  tmux new-session -A -s my-session
fi
```

## State rollups

The sidebar rolls state upward.

A blocked agent makes its pane, tab, and workspace look blocked. A working agent makes the workspace look active. A done agent stays visible until you view it.

This is the main Herdr workflow: start several agents, let them work in parallel, and use the sidebar to see which project needs a decision, which one is still running, and which one is ready to review.

## Custom agent labels

You can rename an agent target for display:

```bash
herdr agent rename w1:p1 reviewer
herdr agent rename reviewer --clear
```

Targets accept a unique live agent name or the pane ID that currently hosts the agent. Terminal IDs and bare agent-kind labels are not accepted.

## Custom status labels

Integrations report lifecycle state as semantic state only. Add display customization separately with pane metadata tokens.

```bash
herdr pane report-agent w1:p1 \
  --source custom:indexer \
  --agent docs-bot \
  --state working

herdr pane report-metadata w1:p1 \
  --source custom:indexer-display \
  --token summary=indexing
```

`state` controls waits, notifications, and rollups. The `summary` token is display-only and can be used as `$summary` in an Agent sidebar row.

Agent sidebar rows can also opt into `terminal_title` or `terminal_title_stripped`; neither appears in the default rows. The first shows the latest safety-normalized OSC 0/2 terminal title. The second removes one recognized leading activity or spinner glyph and following whitespace. Herdr owns these values on the server; they are ephemeral across a cold restart and remain independent of metadata titles and semantic agent state. Spinner animation can therefore update the raw title without producing a pane update when the stripped text stays the same.

## Attach directly to an agent

Attach your current terminal to one agent terminal instead of the full Herdr UI:

```bash
herdr agent attach reviewer
```

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Scroll with the mouse wheel or plain page up/page down. Normal input jumps back to the bottom.

Use `--takeover` if another direct attach client already owns input:

```bash
herdr agent attach reviewer --takeover
```

Use `herdr terminal attach <terminal_id>` when you want the same direct attach behavior for a non-agent terminal.
