# code-review（任务级规则，`--task review` 触发）

审核是只读任务：不改代码、不改配置、不顺手修无关问题；结论以证据为准。

## 输出格式

固定四级，按严重度排列；没有发现的级别保留标题并写「无」：

```text
严重：
- <文件:符号> <触发条件与后果> <建议>
中：
- ...
轻：
- ...
结论：可合入 / 需修改后复审 / 拒绝（附一句理由）
```

## 审核纪律

- 先运行 resolver 拿到本批 diff 的领域规则全集，再逐条对照；不要凭记忆审。
- 每项发现必须给出触发条件与后果，只有可证明的矛盾才算缺陷；规范性「必须 /
  不得」、兼容别名、算法阶段编号不自动等于问题。
- 关键跨域路径（协议字段、端点形状、状态所有者、身份/恢复）看真实调用点，
  不满足于类型通过；`tests/fixtures/endpoint-method-shapes-v1.json` 与冻结
  codec 相关改动一律升级为严重项核对。
- 性能面：命中乘法路径（见 `app-render.md`）的改动要求有固定几何 1/15 pane
  的扩展数据或等价架构测试依据，否则记为「中」。
- 文档漂移：命令、端口、版本号与源码真源不一致记「轻」，安全门描述与实际
  CI 触发面不一致记「中」。
- 修后复审只验证修复本身，不重开范围；三轮仍阻塞则写清诊断与缺失条件。
